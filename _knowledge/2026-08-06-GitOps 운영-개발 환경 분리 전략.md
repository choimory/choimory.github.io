## 개요

GitOps에서 중요한 핵심은 Git 저장소에 선언된 상태가 클러스터의 "desired state"가 된다는 점입니다. 따라서 운영과 개발이 모두 auto-sync로 동작한다면, Git에 반영된 변경이 자동으로 각 환경에 적용됩니다.

이때 운영과 개발이 같은 브랜치, 같은 경로, 같은 매니페스트를 바라보면 개발 변경이 운영에 바로 반영될 수 있습니다. 그래서 핵심은 단순히 브랜치를 나누는 것이 아니라, 환경별 desired state를 명확히 분리하는 것입니다.

---

## 결론

운영과 개발이 둘 다 auto-sync라면 브랜치를 나누는 것이 맞는 경우가 많습니다.

다만 반드시 브랜치만이 정답은 아닙니다. 다음 둘 중 하나는 반드시 분리되어야 합니다.

- 브랜치 분리
- 경로 분리

즉, 운영과 개발이 같은 desired state를 공유하지 않도록 만드는 것이 핵심입니다.

---

## 왜 분리해야 하는가

### 개발 변경의 운영 반영 위험

개발 환경에서는 실험용 설정, 임시 이미지 태그, 낮은 리소스 제한, 디버그 옵션이 들어갈 수 있습니다.

운영과 개발이 같은 Git 경로를 바라보면 이런 변경이 운영에도 자동 반영될 수 있습니다.

### 롤백 단위 혼란

개발은 최신 커밋을 따라가야 할 수 있고, 운영은 안정 버전으로 되돌아가야 할 수 있습니다.

같은 브랜치와 같은 경로를 공유하면 운영만 특정 버전으로 롤백하기가 어려워집니다.

### 승인 흐름 분리 부족

운영 배포는 PR 승인, 보호 브랜치, 릴리즈 태그, 코드 오너 승인 같은 안전장치가 필요합니다.

개발과 운영이 같은 흐름이면 운영 배포의 통제력이 약해집니다.

---

## 추천 구조 1: 브랜치 분리

브랜치를 기준으로 개발과 운영을 분리하는 방식입니다.

```
dev branch  -> dev cluster 또는 dev namespace
main branch -> prod cluster 또는 prod namespace
```

Argo CD 기준으로는 다음처럼 구성할 수 있습니다.

```
dev app  -> repo: dev branch, path: overlays/dev
prod app -> repo: main branch, path: overlays/prod
```

이 방식은 개발과 운영의 배포 흐름이 명확히 갈라져서 직관적입니다.

### 브랜치 분리가 특히 좋은 경우

- 개발은 자주 깨져도 되는 경우
- 운영은 승인된 릴리즈만 반영해야 하는 경우
- 개발과 운영의 배포 주기가 다른 경우
- 운영 롤백을 Git 기준으로 명확히 해야 하는 경우
- 운영 브랜치 접근 권한을 제한해야 하는 경우

---

## 추천 구조 2: 같은 브랜치 + 경로 분리

하나의 브랜치를 사용하되 환경별 경로를 분리하는 방식입니다.

```
main
└─ envs
   ├─ dev
   └─ prod
```

Argo CD 기준으로는 다음처럼 구성할 수 있습니다.

```
dev app  -> repo: main, path: envs/dev
prod app -> repo: main, path: envs/prod
```

이 방식도 많이 사용됩니다. 대신 운영 경로에는 CODEOWNERS, PR 승인, 보호 규칙이 필요합니다.

### 같은 브랜치 + 경로 분리가 괜찮은 경우

- PR 리뷰가 잘 지켜지는 경우
- `envs/dev`, `envs/prod`가 완전히 분리되어 있는 경우
- 운영 경로에 CODEOWNERS 보호가 걸려 있는 경우
- 이미지 태그가 환경별로 명확히 고정되어 있는 경우

---

## 추천 디렉터리 구조

가장 무난한 구조는 Kustomize의 base/overlays 형태입니다.

```
repo
├─ base
└─ overlays
   ├─ dev
   └─ prod
```

각 환경은 공통 base를 공유하되, 실제 배포 설정은 overlay에서 분리합니다.

```
dev  -> overlays/dev  auto-sync
prod -> overlays/prod auto-sync
```

이렇게 하면 공통 매니페스트는 재사용하면서도 환경별 차이를 안전하게 관리할 수 있습니다.

---

## 운영 환경 보호 전략

운영도 auto-sync를 켤 수는 있습니다. 다만 다음 조건을 같이 갖추는 것이 좋습니다.

```
prod는 main 브랜치만 바라봄
prod 변경은 PR 승인 필수
prod 경로는 CODEOWNERS로 보호
prod 이미지 태그는 latest 금지
prod 이미지는 semver 또는 git sha로 고정
prod auto-sync에는 prune/self-heal 정책을 신중히 적용
```

운영 auto-sync는 편리하지만, Git에 merge되는 순간 운영에 반영될 수 있기 때문에 Git merge 과정 자체가 배포 승인 절차가 됩니다.

---

## 전체 요약

운영과 개발이 둘 다 auto-sync라면 같은 desired state를 공유하면 안 됩니다.

가장 중요한 원칙은 다음입니다.

```
dev  -> dev 브랜치 또는 envs/dev
prod -> main 브랜치 또는 envs/prod
```

브랜치 분리는 운영과 개발의 배포 흐름을 명확히 나누는 데 좋고, 같은 브랜치 + 경로 분리는 단순한 저장소 구조를 유지하는 데 좋습니다.

가장 무난한 추천은 `base/overlays` 구조를 사용하고, 운영은 PR 승인, 보호 브랜치, CODEOWNERS, 고정 이미지 태그를 함께 적용하는 방식입니다.
