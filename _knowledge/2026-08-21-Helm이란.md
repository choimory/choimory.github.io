# Helm이란

## 개요

Helm은 Kubernetes 애플리케이션을 "패키지" 형태로 설치, 업그레이드, 롤백, 삭제할 수 있게 해주는 도구입니다.

Kubernetes에서 직접 `Deployment`, `Service`, `Ingress`, `ConfigMap`, `Secret` 같은 YAML을 하나씩 관리하면 환경별 차이와 반복 설정이 많아집니다. Helm은 이런 YAML 묶음을 템플릿화해서 "운영/개발 환경별 값만 바꿔 배포"할 수 있게 해줍니다.

쉽게 말하면 Helm은 "Kubernetes용 패키지 매니저"입니다.

---

## Helm이 필요한 이유

Kubernetes 리소스를 직접 관리하면 보통 이런 문제가 생깁니다.

```
deployment.yaml
service.yaml
ingress.yaml
configmap.yaml
secret.yaml
hpa.yaml
```

서비스가 많아질수록 YAML 파일이 늘어나고, 개발/운영 환경별로 값도 달라집니다.

예를 들면 다음 값들이 환경마다 달라집니다.

```yaml
replicaCount: 2
image:
  repository: my-app
  tag: dev
ingress:
  host: dev.example.com
resources:
  requests:
    cpu: 100m
    memory: 256Mi
```

운영에서는 이렇게 바뀔 수 있습니다.

```yaml
replicaCount: 4
image:
  tag: prod
ingress:
  host: example.com
resources:
  requests:
    cpu: 500m
    memory: 1Gi
```

Helm을 쓰면 공통 Kubernetes YAML은 템플릿으로 만들고, 환경별 차이는 `values.yaml`로 분리할 수 있습니다.

---

## Helm의 핵심 개념

### Chart

Chart는 Helm 패키지입니다.

하나의 애플리케이션을 배포하기 위한 Kubernetes YAML 템플릿 묶음입니다.

예를 들어 Spring Boot API 하나를 배포한다면 다음 리소스들이 하나의 Chart에 들어갈 수 있습니다.

```
Deployment
Service
Ingress
ConfigMap
Secret
HPA
ServiceAccount
```

즉, Chart는 "이 서비스를 Kubernetes에 띄우기 위한 설계도"입니다.

---

### Release

Release는 Chart를 실제 Kubernetes 클러스터에 설치한 결과물입니다.

같은 Chart를 여러 번 설치해도 Release 이름이 다르면 별개의 애플리케이션처럼 관리할 수 있습니다.

예를 들어 같은 `backend-api` Chart를 다음처럼 설치할 수 있습니다.

```bash
helm install backend-dev ./backend-chart -f values-dev.yaml
helm install backend-prod ./backend-chart -f values-prod.yaml
```

여기서 `backend-dev`, `backend-prod`가 Release입니다.

---

### Values

Values는 Chart 템플릿에 주입되는 설정값입니다.

예를 들어 `values.yaml`에 이렇게 적습니다.

```yaml
replicaCount: 2

image:
  repository: my-registry/backend-api
  tag: dev

service:
  type: ClusterIP
  port: 8080

ingress:
  enabled: true
  host: dev-api.example.com
```

그리고 Deployment 템플릿에서는 이렇게 사용합니다.

```yaml
replicas: {{ .Values.replicaCount }}
```

결과적으로 Helm이 값을 치환해서 실제 Kubernetes YAML을 만들어냅니다.

---

## Helm Chart 구조

일반적인 Helm Chart 구조는 다음과 같습니다.

```
my-app/
  Chart.yaml
  values.yaml
  templates/
    deployment.yaml
    service.yaml
    ingress.yaml
    configmap.yaml
    hpa.yaml
  charts/
```

### Chart.yaml

Chart 자체의 메타데이터입니다.

```yaml
apiVersion: v2
name: my-app
description: My application Helm chart
type: application
version: 0.1.0
appVersion: "1.0.0"
```

주요 필드는 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| `name` | Chart 이름 |
| `version` | Chart 버전 |
| `appVersion` | 애플리케이션 버전 |
| `type` | application 또는 library |

---

### values.yaml

기본 설정값입니다.

```yaml
replicaCount: 1

image:
  repository: nginx
  tag: latest
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

환경별로 파일을 나누면 보통 이렇게 구성합니다.

```
values-dev.yaml
values-prod.yaml
values-local.yaml
```

---

### templates 디렉터리

Kubernetes YAML 템플릿이 들어가는 곳입니다.

예를 들어 `templates/deployment.yaml`은 다음처럼 작성할 수 있습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.service.port }}
```

## Helm 주요 명령어

### Chart 생성

```bash
helm create my-app
```

기본 Chart 구조를 자동으로 만들어줍니다.

---

### 템플릿 결과 확인

```bash
helm template my-app ./my-app
```

실제 클러스터에 배포하지 않고, Helm이 렌더링한 Kubernetes YAML만 확인합니다.

개발할 때 매우 자주 사용합니다.

---

### 설치

```bash
helm install my-app ./my-app
```

환경별 values 파일을 적용하려면 다음처럼 합니다.

```bash
helm install my-app ./my-app -f values-dev.yaml
```

---

### 업그레이드

```bash
helm upgrade my-app ./my-app -f values-dev.yaml
```

설치되어 있지 않으면 설치하고, 있으면 업그레이드하려면 다음 명령어를 많이 씁니다.

```bash
helm upgrade --install my-app ./my-app -f values-dev.yaml
```

---

### 롤백

```bash
helm rollback my-app 1
```

Release의 이전 revision으로 되돌릴 수 있습니다.

---

### Release 목록 확인

```bash
helm list
```

네임스페이스까지 지정하려면 다음처럼 합니다.

```bash
helm list -n dev
```

---

### 삭제

```bash
helm uninstall my-app
```

네임스페이스를 지정하려면 다음처럼 합니다.

```bash
helm uninstall my-app -n dev
```

## Helm과 Kubernetes YAML의 관계

Helm은 Kubernetes를 대체하는 도구가 아닙니다.

Helm은 결국 Kubernetes YAML을 생성해서 Kubernetes API Server에 적용하는 도구입니다.

흐름은 다음과 같습니다.

```
Chart + values.yaml
        ↓
Helm template rendering
        ↓
Kubernetes YAML
        ↓
kubectl apply와 유사하게 클러스터에 반영
```

즉, Helm을 잘 쓰려면 Kubernetes의 기본 리소스 구조도 알아야 합니다.

---

## 운영/개발 환경 분리 방식

실무에서는 보통 Chart는 공통으로 두고, values 파일만 환경별로 나눕니다.

```
charts/
  backend-api/
    Chart.yaml
    values.yaml
    templates/

values/
  dev.yaml
  prod.yaml
```

배포는 다음처럼 합니다.

```bash
helm upgrade --install backend-api ./charts/backend-api -f values/dev.yaml -n dev
```

```bash
helm upgrade --install backend-api ./charts/backend-api -f values/prod.yaml -n prod
```

이렇게 하면 동일한 Chart를 사용하면서 개발/운영 환경을 분리할 수 있습니다.

## GitOps에서 Helm 사용 방식

GitOps에서는 Helm을 직접 CLI로 실행하기보다 Argo CD나 Flux 같은 도구가 Helm Chart를 읽어서 배포하는 구조를 많이 씁니다.

예를 들어 Argo CD에서는 다음과 같은 구조가 가능합니다.

```
GitOps Repository
  ├── apps/
  │   ├── backend-dev.yaml
  │   └── backend-prod.yaml
  ├── charts/
  │   └── backend-api/
  └── values/
      ├── dev.yaml
      └── prod.yaml
```

Argo CD Application에서 Helm Chart와 values 파일을 지정합니다.

```yaml
source:
  repoURL: https://github.com/example/gitops-repo
  targetRevision: main
  path: charts/backend-api
  helm:
    valueFiles:
      - ../../values/dev.yaml
```

이 구조에서는 배포 명령을 사람이 직접 실행하지 않아도 됩니다.

Git에 변경사항을 push하면 Argo CD가 변경을 감지하고 클러스터에 반영합니다.

---

## Helm Repository

Helm Repository는 Chart를 저장하고 배포하는 저장소입니다.

예를 들면 다음과 같습니다.

```
Helm Chart
  ↓
Helm Repository
  ↓
Argo CD 또는 Helm CLI가 참조
  ↓
Kubernetes 배포
```

대표적으로 다음 방식들이 있습니다.

| 방식 | 설명 |
| --- | --- |
| HTTP Helm Repository | 전통적인 Helm Chart 저장소 |
| OCI Registry | Container Registry에 Helm Chart를 저장 |
| Git Repository | GitOps에서 Chart를 Git에 직접 보관 |

최근에는 Container Registry에 Helm Chart를 OCI 방식으로 저장하는 구성도 많이 사용합니다.

예시는 다음과 같습니다.

```bash
helm package ./my-app
helm push my-app-0.1.0.tgz oci://my-registry.example.com/helm
```

## Helm을 쓸 때 주의할 점

### 템플릿이 너무 복잡해질 수 있음

Helm 템플릿은 조건문, 반복문, 함수 등을 지원합니다.

```yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{- end }}
```

하지만 Chart가 너무 복잡해지면 YAML보다 더 읽기 어려워질 수 있습니다.

공통화는 하되, 과도한 추상화는 피하는 것이 좋습니다.

---

### Secret 관리 주의

Helm values 파일에 DB 비밀번호나 API Key를 평문으로 넣으면 위험합니다.

좋은 방식은 다음과 같습니다.

```
External Secrets Operator
Sealed Secrets
SOPS
Vault
Cloud Secret Manager
```

예를 들어 GitOps 환경에서는 `values-prod.yaml`에 비밀번호를 직접 넣지 않고, External Secrets Operator로 외부 Secret Manager에서 가져오는 방식을 많이 씁니다.

---

### 환경별 values 관리

개발/운영 환경 차이를 관리할 때 모든 값을 values 파일에 넣기보다, "환경마다 바뀌는 값"만 분리하는 것이 좋습니다.

예를 들면 다음 값들은 환경별로 분리하기 좋습니다.

```
replicaCount
image.tag
ingress.host
resources
autoscaling
database endpoint
```

반대로 Kubernetes 리소스의 기본 구조는 Chart 템플릿에 유지하는 것이 좋습니다.

---

## Helm과 Kustomize 비교

Helm과 Kustomize는 둘 다 Kubernetes 매니페스트를 관리하는 도구지만 접근 방식이 다릅니다.

| 구분 | Helm | Kustomize |
| --- | --- | --- |
| 방식 | 템플릿 기반 | 오버레이 기반 |
| 핵심 파일 | Chart, values.yaml | kustomization.yaml |
| 장점 | 패키징, 배포, 롤백, 버전 관리 강함 | 순수 YAML 기반이라 단순함 |
| 단점 | 템플릿이 복잡해질 수 있음 | 패키지 관리 기능은 약함 |
| 적합한 경우 | 애플리케이션을 패키지처럼 배포 | 환경별 YAML 차이를 덧씌워 관리 |

간단히 정리하면 다음과 같습니다.

```
Helm = Kubernetes 앱을 패키지화해서 배포
Kustomize = Kubernetes YAML을 환경별로 덧씌워 변형
```

둘을 같이 쓰는 경우도 있습니다.

예를 들어 Helm Chart로 기본 리소스를 만들고, Kustomize로 환경별 patch를 적용하는 방식입니다.

하지만 처음에는 하나만 선택하는 것이 관리하기 쉽습니다.

## 추천 구조

GitOps 기반 Kubernetes 운영/개발 환경이라면 다음 구조가 깔끔합니다.

```
gitops-repo/
  apps/
    dev/
      backend-api.yaml
      frontend.yaml
    prod/
      backend-api.yaml
      frontend.yaml

  charts/
    backend-api/
    frontend/

  values/
    dev/
      backend-api.yaml
      frontend.yaml
    prod/
      backend-api.yaml
      frontend.yaml
```

배포 흐름은 다음과 같습니다.

```
개발자
  ↓
Application Source Code Push
  ↓
Jenkins Build
  ↓
Container Registry Push
  ↓
GitOps Repository image tag 변경
  ↓
Argo CD Sync
  ↓
Helm Chart 렌더링
  ↓
Kubernetes 배포
```

이 구조에서는 Helm이 "Kubernetes 리소스 템플릿 및 배포 패키지" 역할을 하고, GitOps Repository가 "현재 클러스터 상태의 선언적 원본" 역할을 합니다.

## 전체 요약

Helm은 Kubernetes 애플리케이션을 패키지처럼 관리하는 도구입니다.

핵심 개념은 다음과 같습니다.

| 개념 | 설명 |
| --- | --- |
| Chart | Kubernetes 리소스 템플릿 묶음 |
| Release | Chart를 클러스터에 설치한 결과 |
| Values | 환경별 설정값 |
| Helm Repository | Chart를 저장하는 저장소 |

실무에서는 보통 다음처럼 사용합니다.

```
공통 Chart
+ 개발 values.yaml
+ 운영 values.yaml
= 환경별 Kubernetes 배포
```

GitOps 환경에서는 Helm을 직접 실행하기보다 Argo CD나 Flux가 Git Repository의 Helm Chart와 values 파일을 읽어 Kubernetes에 반영하는 구조가 많이 사용됩니다.

정리하면 Helm은 "Kubernetes YAML을 재사용 가능하고 환경별로 관리 가능한 배포 패키지로 만드는 도구"입니다.

# Helm과 ArgoCD의 차이

## 개요

Helm과 ArgoCD는 둘 다 Kubernetes 배포와 관련된 도구이지만, 역할이 다릅니다.

간단히 말하면 Helm은 "Kubernetes 애플리케이션을 패키징하고 템플릿화하는 도구"이고, ArgoCD는 "Git에 선언된 상태를 Kubernetes 클러스터에 자동으로 동기화하는 GitOps 배포 도구"입니다.

즉, Helm은 "무엇을 어떻게 YAML로 만들지"에 가깝고, ArgoCD는 "Git에 있는 원하는 상태를 클러스터에 계속 맞출지"에 가깝습니다.

---

## 핵심 차이

| 구분 | Helm | ArgoCD |
| --- | --- | --- |
| 주요 역할 | Kubernetes 앱 패키징, 템플릿 렌더링, 설치 | GitOps 기반 배포 자동화, 상태 동기화 |
| 관리 대상 | Chart, values.yaml, Release | Git Repository, Application, Cluster 상태 |
| 실행 방식 | 사용자가 `helm install/upgrade` 실행 | ArgoCD가 Git을 감시하고 자동/수동 Sync |
| 상태 관리 | Helm Release revision 관리 | Git 상태와 클러스터 상태 비교 |
| 롤백 방식 | Helm revision 기준 롤백 | Git commit 되돌리기 또는 ArgoCD rollback |
| 배포 기준 | CLI 명령 실행 시점 | Git에 선언된 desired state |
| UI | 기본적으로 CLI 중심 | Web UI, CLI, API 제공 |
| GitOps 적합성 | 단독으로는 약함 | GitOps에 특화됨 |
| Helm 사용 가능 여부 | Helm 자체 | ArgoCD 내부에서 Helm Chart 사용 가능 |

---

## Helm은 무엇인가

Helm은 Kubernetes 리소스를 Chart라는 패키지로 묶어 관리하는 도구입니다.

예를 들어 애플리케이션 하나를 배포하려면 보통 다음 YAML들이 필요합니다.

```
Deployment
Service
Ingress
ConfigMap
Secret
HPA
ServiceAccount
```

Helm은 이런 YAML들을 템플릿으로 만들고, 환경별 값은 `values.yaml`로 주입합니다.

예를 들어 다음처럼 사용할 수 있습니다.

```bash
helm upgrade --install backend-api ./charts/backend-api -f values-dev.yaml -n dev
```

이 명령은 Helm Chart를 렌더링해서 Kubernetes 클러스터에 적용합니다.

### Helm의 핵심 역할

Helm의 핵심은 다음입니다.

```
Chart + values.yaml
        ↓
Helm template rendering
        ↓
Kubernetes YAML
        ↓
Cluster 배포
```

즉 Helm은 "YAML을 재사용 가능한 패키지로 만들고, 값만 바꿔 여러 환경에 배포하게 해주는 도구"입니다.

---

## ArgoCD는 무엇인가

ArgoCD는 GitOps 방식으로 Kubernetes 배포를 관리하는 도구입니다.

GitOps에서는 Git Repository가 클러스터의 정답 상태입니다.

예를 들어 Git에 다음과 같은 매니페스트가 있다고 가정합니다.

```
gitops-repo/
  apps/
    dev/
      backend-api.yaml
    prod/
      backend-api.yaml
  charts/
    backend-api/
  values/
    dev.yaml
    prod.yaml
```

ArgoCD는 이 Git Repository를 감시하다가 변경사항이 생기면 Kubernetes 클러스터 상태와 비교합니다.

```
Git Repository의 desired state
        ↓ 비교
현재 Kubernetes Cluster 상태
        ↓
차이가 있으면 Sync
```

### ArgoCD의 핵심 역할

ArgoCD의 핵심은 다음입니다.

```
Git Repository
        ↓
ArgoCD가 변경 감지
        ↓
Kubernetes Cluster와 상태 비교
        ↓
Sync
        ↓
배포 완료
```

즉 ArgoCD는 "Git에 적힌 배포 상태를 클러스터에 계속 맞춰주는 도구"입니다.

---

## 둘의 관계

Helm과 ArgoCD는 경쟁 관계라기보다 같이 쓰는 경우가 많습니다.

ArgoCD는 Kubernetes YAML뿐 아니라 Helm Chart도 배포 소스로 사용할 수 있습니다.

흐름은 다음과 같습니다.

```
GitOps Repository
  ├── Helm Chart
  └── values-dev.yaml
        ↓
ArgoCD
        ↓
Helm template rendering
        ↓
Kubernetes YAML
        ↓
Kubernetes Cluster
```

이때 Helm은 "템플릿 렌더링 도구"로 쓰이고, ArgoCD는 "배포와 동기화 관리자"로 쓰입니다.

즉, ArgoCD가 Helm을 내부적으로 사용해서 Chart를 렌더링한 뒤 Kubernetes에 반영하는 구조입니다.

---

## 예시로 보는 차이

## Helm만 쓰는 경우

Helm만 쓰면 사람이 직접 명령어를 실행해야 합니다.

```bash
helm upgrade --install backend-api ./charts/backend-api -f values-prod.yaml -n prod
```

배포 흐름은 다음과 같습니다.

```
개발자 또는 CI 서버
        ↓
helm upgrade --install 실행
        ↓
Kubernetes Cluster 반영
```

이 방식은 단순하지만, 몇 가지 문제가 생길 수 있습니다.

```
누가 언제 어떤 values로 배포했는지 추적이 어려울 수 있음
클러스터 상태가 Git과 달라져도 자동으로 감지하기 어려움
운영자가 직접 클러스터에 수정한 drift를 관리하기 어려움
배포 권한이 CI 또는 사람에게 직접 필요함
```

---

## ArgoCD와 Helm을 같이 쓰는 경우

ArgoCD와 Helm을 같이 쓰면 사람이 클러스터에 직접 배포하지 않습니다.

대신 Git을 수정합니다.

```
values-prod.yaml의 image tag 변경
        ↓
Git push
        ↓
ArgoCD가 변경 감지
        ↓
Helm Chart 렌더링
        ↓
Kubernetes Cluster Sync
```

예를 들면 Git에 다음 값이 변경됩니다.

```yaml
image:
  repository: my-registry/backend-api
  tag: 1.2.3
```

ArgoCD가 이 변경을 보고 자동 또는 수동으로 배포합니다.

이 구조에서는 Git commit이 배포 이력이 됩니다.

---

## 책임 범위 차이

### Helm의 책임

Helm은 주로 다음을 담당합니다.

```
Kubernetes YAML 템플릿화
환경별 values 주입
Chart 패키징
Release 설치/업그레이드/롤백
의존 Chart 관리
```

즉, Helm은 "배포할 리소스를 만드는 쪽"에 강합니다.

---

### ArgoCD의 책임

ArgoCD는 주로 다음을 담당합니다.

```
Git Repository 감시
클러스터 상태 비교
Sync 수행
Drift 감지
배포 이력 시각화
권한 제어
멀티 클러스터 배포 관리
Web UI 제공
```

즉, ArgoCD는 "Git 기준으로 클러스터 상태를 운영하는 쪽"에 강합니다.

---

## 배포 방식 차이

### Helm 배포 방식

Helm은 명령형 배포에 가깝습니다.

```
내가 지금 이 명령을 실행해서 배포한다
```

예시는 다음과 같습니다.

```bash
helm upgrade --install app ./chart -f values.yaml
```

물론 CI/CD에서 자동화할 수는 있지만, 기본 구조는 "명령 실행"입니다.

---

### ArgoCD 배포 방식

ArgoCD는 선언형 배포에 가깝습니다.

```
Git에 이 상태가 적혀 있으니 클러스터도 이 상태여야 한다
```

예시는 다음과 같습니다.

```
Git의 manifest 변경
        ↓
ArgoCD가 desired state로 인식
        ↓
Cluster에 반영
```

사람이나 CI가 직접 Kubernetes 클러스터에 배포 명령을 내리지 않아도 됩니다.

---

## 롤백 차이

### Helm 롤백

Helm은 Release revision을 기준으로 롤백합니다.

```bash
helm history backend-api
helm rollback backend-api 3
```

이 방식은 Helm이 관리하는 Release 이력을 기준으로 되돌립니다.

---

### ArgoCD 롤백

ArgoCD에서는 보통 Git commit을 되돌리는 방식이 더 자연스럽습니다.

```
문제 있는 commit revert
        ↓
Git push
        ↓
ArgoCD Sync
        ↓
이전 상태로 복구
```

ArgoCD UI에서도 이전 revision으로 rollback할 수 있지만, GitOps 원칙상 Git 이력을 되돌리는 방식이 더 명확합니다.

---

## 상태 불일치 감지 차이

Helm만 쓰면 배포 이후 누군가 클러스터에서 직접 리소스를 수정해도 Helm이 계속 감시하지는 않습니다.

예를 들어 누군가 직접 다음 명령을 실행했다고 가정합니다.

```bash
kubectl scale deployment backend-api --replicas=10
```

Helm은 그 순간 자동으로 "Git 또는 values와 다르다"고 알려주지 않습니다.

반면 ArgoCD는 Git에 선언된 replicas 값과 실제 클러스터 값이 다르면 상태를 `OutOfSync`로 표시할 수 있습니다.

```
Git desired state: replicas 3
Cluster live state: replicas 10
        ↓
ArgoCD: OutOfSync 감지
```

이것이 GitOps에서 ArgoCD를 쓰는 큰 이유입니다.

---

## CI/CD에서의 위치 차이

일반적인 CI/CD 흐름에서는 둘의 위치가 다릅니다.

```
개발자
  ↓
Git Repository에 코드 Push
  ↓
Jenkins/GitHub Actions
  ↓
Docker Image Build
  ↓
Container Registry Push
  ↓
GitOps Repository의 image tag 변경
  ↓
ArgoCD Sync
  ↓
Kubernetes 배포
```

이 구조에서 Helm과 ArgoCD의 역할은 다음과 같습니다.

```
Helm:
Kubernetes 리소스 템플릿 제공

ArgoCD:
GitOps Repository 변경 감지 후 클러스터에 배포
```

즉, Jenkins 같은 CI 도구가 이미지를 만들고, Helm이 배포 YAML을 만들 수 있게 해주고, ArgoCD가 실제 클러스터 상태를 Git 기준으로 맞춥니다.

---

## 실무에서 추천하는 조합

Kubernetes 운영/개발 환경을 나눠 관리한다면 보통 다음 조합이 좋습니다.

```
Helm Chart
+ 환경별 values.yaml
+ ArgoCD Application
```

예시 구조는 다음과 같습니다.

```
gitops-repo/
  charts/
    backend-api/
      Chart.yaml
      values.yaml
      templates/
        deployment.yaml
        service.yaml
        ingress.yaml

  values/
    dev/
      backend-api.yaml
    prod/
      backend-api.yaml

  argocd/
    dev/
      backend-api-application.yaml
    prod/
      backend-api-application.yaml
```

ArgoCD Application에서는 Helm Chart와 values 파일을 지정합니다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: backend-api-dev
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/gitops-repo
    targetRevision: main
    path: charts/backend-api
    helm:
      valueFiles:
        - ../../values/dev/backend-api.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

이렇게 하면 ArgoCD가 Helm Chart를 읽고, dev values를 적용해서 dev namespace에 배포합니다.

---

## 언제 Helm만 써도 되는가

다음 상황에서는 Helm만 써도 충분할 수 있습니다.

```
클러스터가 1개뿐임
서비스 수가 적음
배포를 사람이 직접 해도 큰 문제가 없음
GitOps까지 도입할 필요가 없음
운영 환경이 단순함
```

예를 들어 개인 프로젝트나 작은 내부 도구라면 다음 명령만으로 충분할 수 있습니다.

```bash
helm upgrade --install my-app ./chart -f values.yaml
```

---

## 언제 ArgoCD가 필요한가

다음 상황에서는 ArgoCD가 유리합니다.

```
운영/개발/스테이징 환경이 나뉨
서비스가 여러 개임
배포 이력을 Git으로 남기고 싶음
클러스터 직접 접근을 줄이고 싶음
클러스터 상태 drift를 감지하고 싶음
멀티 클러스터를 관리해야 함
운영 배포를 승인 기반으로 관리하고 싶음
```

특히 운영 환경에서는 사람이 직접 `kubectl`이나 `helm upgrade`를 실행하는 방식보다, Git 변경을 통해 배포하고 ArgoCD가 Sync하는 방식이 더 추적 가능하고 안전합니다.

---

## 한 줄 비유

Helm과 ArgoCD를 비유하면 다음과 같습니다.

```
Helm = Kubernetes 앱 설치 패키지를 만드는 도구
ArgoCD = Git에 적힌 설치 상태대로 클러스터를 유지하는 배포 관리자
```

또 다른 비유로는 다음과 같습니다.

```
Helm = 요리 레시피와 재료 비율표
ArgoCD = 레시피대로 주방 상태를 계속 점검하고 맞추는 관리자
```

---

## 전체 요약

Helm과 ArgoCD의 차이는 "패키징 도구냐, GitOps 배포 도구냐"입니다.

| 질문 | 답 |
| --- | --- |
| Helm은 무엇인가 | Kubernetes YAML을 Chart와 values로 패키징하는 도구 |
| ArgoCD는 무엇인가 | Git 상태를 기준으로 Kubernetes 클러스터를 동기화하는 GitOps 도구 |
| 둘은 대체 관계인가 | 완전한 대체 관계가 아니라 함께 쓰는 경우가 많음 |
| Helm만 쓰면 | CLI 또는 CI가 직접 배포 |
| ArgoCD를 쓰면 | Git 변경을 기준으로 자동/수동 Sync |
| 실무 추천 | Helm Chart + 환경별 values + ArgoCD Application |

정리하면 Helm은 "배포할 Kubernetes 리소스를 템플릿으로 만드는 도구"이고, ArgoCD는 "Git에 있는 배포 상태를 클러스터에 반영하고 유지하는 도구"입니다.
