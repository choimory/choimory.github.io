# DTO 변환 책임 위치

## 개요

DTO 변환 책임 위치는 다음 질문으로 정리할 수 있습니다.

> Entity와 DTO 사이의 변환 로직을 어느 클래스에 둘 것인가?
> 

Spring Boot 프로젝트에서는 보통 다음 방식이 사용됩니다.

```
1. DTO 내부 정적 팩토리 메서드
2. DTO 내부 인스턴스 메서드
3. Service 계층
4. 별도 Mapper 클래스
5. MapStruct 같은 매핑 라이브러리
```

정답이 하나로 고정되어 있는 것은 아닙니다. 프로젝트 규모, 계층 간 의존성, 변환 로직의 복잡도에 따라 선택해야 합니다.

가장 일반적인 기준은 다음과 같습니다.

```
Entity → Response DTO
Response DTO가 변환 책임을 가짐

Request DTO → Entity
Service 또는 도메인 객체가 생성 책임을 가짐
```

---

## Entity에서 Response DTO로 변환

### DTO의 `from` 메서드 사용

Spring Boot 프로젝트에서 가장 많이 사용하는 방식입니다.

```java
public record MemberResponse(
    Long id,
    String name,
    String email
) {

    public static MemberResponse from(Member member) {
        return new MemberResponse(
            member.getId(),
            member.getName(),
            member.getEmail()
        );
    }
}
```

Service에서는 다음과 같이 사용합니다.

```java
Member member = memberRepository.findById(memberId)
    .orElseThrow(MemberNotFoundException::new);

return MemberResponse.from(member);
```

### 변환 책임의 방향

```
MemberResponse → Member를 알고 있음
Member → MemberResponse를 알지 않음
```

이 구조가 중요한 이유는 Entity가 API DTO에 의존하지 않기 때문입니다.

```java
// 권장하지 않는 예시
@Entity
public class Member {

    public MemberResponse toResponse() {
        return new MemberResponse(
            id,
            name,
            email
        );
    }
}
```

이렇게 만들면 도메인 계층의 Entity가 표현 계층의 DTO를 알아야 합니다.

```
도메인 계층 → API 표현 계층
```

일반적으로 의존성 방향이 부자연스럽습니다.

### 장점

- 변환 코드가 DTO 내부에 모입니다.
- Service 코드가 간결해집니다.
- Entity가 DTO를 알 필요가 없습니다.
- DTO 구조가 변경될 때 관련 변환 코드도 함께 확인할 수 있습니다.

### 단점

- DTO가 Entity에 직접 의존합니다.
- 변환 방식이 복잡해지면 DTO 코드가 비대해질 수 있습니다.
- 여러 Entity를 조합하면 `from` 메서드가 지나치게 복잡해질 수 있습니다.

---

## Request DTO에서 Entity로 변환

### DTO의 `toEntity` 사용

많이 사용하는 방식 중 하나입니다.

```java
public record CreateMemberRequest(
    String name,
    String email
) {

    public Member toEntity() {
        return Member.create(name, email);
    }
}
```

사용 코드는 다음과 같습니다.

```java
Member member = request.toEntity();
memberRepository.save(member);
```

코드가 간결하고 직관적입니다.

하지만 Request DTO가 도메인 객체의 생성 방법을 알아야 한다는 문제가 있습니다.

```
Request DTO → Entity
```

단순한 CRUD 프로젝트에서는 충분히 사용할 수 있지만, 도메인 규칙이 복잡한 프로젝트에서는 주의해야 합니다.

---

## Service에서 Entity를 생성하는 방식

Request DTO는 단순히 입력값만 보관하고, Entity 생성은 Service에서 처리합니다.

```java
public record CreateMemberRequest(
    String name,
    String email
) {
}
```

```java
@Transactional
public Long createMember(CreateMemberRequest request) {
    Member member = Member.create(
        request.name(),
        request.email()
    );

    return memberRepository.save(member).getId();
}
```

### 장점

- Request DTO가 Entity 생성 방법을 알지 않습니다.
- 애플리케이션 흐름이 Service에 명시적으로 나타납니다.
- DTO와 도메인 계층의 결합도가 낮아집니다.

### 단점

- Service에 필드 복사 코드가 반복될 수 있습니다.
- Service 클래스가 점점 길어질 수 있습니다.
- 여러 곳에서 동일한 변환을 하면 중복이 발생할 수 있습니다.

---

## Entity가 생성 책임을 가지는 방식

Entity가 정적 팩토리 메서드를 통해 자신의 생성 규칙을 관리합니다.

```java
@Entity
public class Member {

    @Id
    @GeneratedValue
    private Long id;

    private String name;
    private String email;

    protected Member() {
    }

    private Member(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public static Member create(String name, String email) {
        validateName(name);
        validateEmail(email);

        return new Member(name, email);
    }

    private static void validateName(String name) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("이름은 필수입니다.");
        }
    }

    private static void validateEmail(String email) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("이메일 형식이 올바르지 않습니다.");
        }
    }
}
```

Service는 DTO에서 값을 꺼내 Entity의 생성 메서드를 호출합니다.

```java
Member member = Member.create(
    request.name(),
    request.email()
);
```

이 방식은 객체 생성 규칙을 Entity 내부에 유지할 수 있습니다.

```
DTO: 입력값 전달
Service: 흐름 조정
Entity: 생성 규칙과 도메인 불변식 보장
```

도메인 중심 설계에서는 이 구성이 비교적 자연스럽습니다.

---

## 별도 Mapper 클래스 사용

변환 로직을 전담하는 클래스를 만드는 방식입니다.

```java
@Component
public class MemberMapper {

    public Member toEntity(CreateMemberRequest request) {
        return Member.create(
            request.name(),
            request.email()
        );
    }

    public MemberResponse toResponse(Member member) {
        return new MemberResponse(
            member.getId(),
            member.getName(),
            member.getEmail()
        );
    }
}
```

Service에서는 다음과 같이 사용합니다.

```java
@Service
@RequiredArgsConstructor
public class MemberService {

    private final MemberRepository memberRepository;
    private final MemberMapper memberMapper;

    public MemberResponse findMember(Long memberId) {
        Member member = memberRepository.findById(memberId)
            .orElseThrow(MemberNotFoundException::new);

        return memberMapper.toResponse(member);
    }
}
```

### 장점

- DTO와 Entity 모두 변환 책임에서 자유로워집니다.
- 복잡한 변환을 한곳에서 관리할 수 있습니다.
- 여러 객체를 조합하는 변환에 적합합니다.
- 변환 로직만 별도로 테스트하기 쉽습니다.

### 단점

- 클래스 수가 증가합니다.
- 단순한 변환에도 Mapper를 만들면 과도한 구조가 될 수 있습니다.
- 변환 코드의 위치를 찾아 이동해야 합니다.

---

## Mapper를 사용하기 좋은 경우

단순한 필드 복사라면 DTO의 `from`으로 충분합니다.

```java
MemberResponse.from(member);
```

다음과 같이 변환이 복잡하면 별도 Mapper가 적합합니다.

```java
public OrderResponse toResponse(
    Order order,
    Member member,
    List<OrderItem> orderItems,
    Map<Long, Product> products
) {
    // 여러 객체 조합
    // 금액 계산
    // 상태 문자열 변환
    // 하위 DTO 생성
}
```

다음 조건 중 여러 개가 해당하면 Mapper 분리를 고려할 수 있습니다.

- 여러 Entity를 조합해야 하는 경우
- 하위 DTO 목록 변환이 많은 경우
- 계산이나 포맷 변경이 포함되는 경우
- 동일한 변환을 여러 곳에서 재사용하는 경우
- DTO 내부 코드가 지나치게 길어지는 경우
- 외부 API 객체와 내부 도메인 객체를 변환하는 경우

---

## Service에 변환 로직을 직접 작성하는 방식

```java
public MemberResponse findMember(Long memberId) {
    Member member = memberRepository.findById(memberId)
        .orElseThrow(MemberNotFoundException::new);

    return new MemberResponse(
        member.getId(),
        member.getName(),
        member.getEmail()
    );
}
```

작은 프로젝트에서는 충분히 사용할 수 있습니다.

하지만 변환 로직이 여러 Service 메서드에 반복되기 시작하면 문제가 됩니다.

```java
return new MemberResponse(
    member.getId(),
    member.getName(),
    member.getEmail()
);
```

동일한 코드가 여러 곳에서 반복되면 DTO 변경 시 모든 코드를 찾아 수정해야 합니다.

따라서 Service 직접 변환은 다음 경우에 적합합니다.

```
일회성 변환
변환 코드가 매우 짧음
재사용 가능성이 없음
프로젝트 규모가 작음
```

반복되는 순간 DTO의 `from`이나 Mapper로 이동하는 것이 좋습니다.

## 변환 책임을 Controller에 두는 방식

Controller에서 직접 변환하는 방식입니다.

```java
@GetMapping("/{memberId}")
public MemberResponse findMember(
    @PathVariable Long memberId
) {
    Member member = memberService.findMember(memberId);

    return MemberResponse.from(member);
}
```

이 구조도 사용할 수 있지만, Service가 Entity를 외부로 반환한다는 문제가 발생할 수 있습니다.

```java
public Member findMember(Long memberId) {
    return memberRepository.findById(memberId)
        .orElseThrow(MemberNotFoundException::new);
}
```

Service가 Entity를 반환하면 다음 문제가 생길 수 있습니다.

- Controller가 영속성 객체에 직접 의존합니다.
- 지연 로딩 문제가 Controller까지 노출될 수 있습니다.
- 트랜잭션 경계 밖에서 연관 객체 접근 문제가 생길 수 있습니다.
- API 계층이 도메인 내부 구조를 많이 알게 됩니다.

일반적으로 Service가 필요한 DTO까지 만들어 반환하는 편이 안전합니다.

```java
public MemberResponse findMember(Long memberId) {
    Member member = memberRepository.findById(memberId)
        .orElseThrow(MemberNotFoundException::new);

    return MemberResponse.from(member);
}
```

## 변환 방향별 권장 방식

### Entity에서 Response DTO

가장 무난한 방식입니다.

```java
MemberResponse.from(member);
```

변환이 복잡하면 Mapper를 사용합니다.

```java
memberMapper.toResponse(member);
```

Entity에 다음과 같은 메서드를 두는 것은 일반적으로 피하는 편이 좋습니다.

```java
member.toResponse();
```

Entity가 특정 API DTO를 알게 되기 때문입니다.

---

### Request DTO에서 Entity

단순 CRUD라면 다음 방식도 가능합니다.

```java
request.toEntity();
```

도메인 규칙이 중요한 경우에는 Service에서 Entity 팩토리 메서드를 호출하는 편이 좋습니다.

```java
Member member = Member.create(
    request.name(),
    request.email()
);
```

변환 과정이 복잡하거나 여러 곳에서 재사용되면 Mapper를 사용할 수 있습니다.

```java
Member member = memberMapper.toEntity(request);
```

## 권장 의존성 방향

일반적인 계층 구조는 다음과 같습니다.

```
Controller
    ↓
Application Service
    ↓
Domain
    ↓
Infrastructure
```

DTO는 주로 Controller 또는 Application 계층에 위치합니다.

```
presentation
 ├─ request
 └─ response

application
 └─ service

domain
 ├─ entity
 └─ repository
```

이때 도메인 객체가 DTO를 참조하지 않도록 하는 것이 중요합니다.

```
DTO → Domain: 가능
Domain → DTO: 가급적 피함
```

도메인 계층은 HTTP 요청, JSON 응답, API 스펙과 독립적으로 유지하는 편이 좋습니다.

## Kotlin에서의 구현

### Response DTO의 `from`

```kotlin
data class MemberResponse(
    val id: Long,
    val name: String,
    val email: String,
) {
    companion object {
        fun from(member: Member): MemberResponse {
            return MemberResponse(
                id = member.id,
                name = member.name,
                email = member.email,
            )
        }
    }
}
```

사용 방법입니다.

```kotlin
return MemberResponse.from(member)
```

### Request DTO와 Entity 생성

```kotlin
data class CreateMemberRequest(
    val name: String,
    val email: String,
)
```

```kotlin
class Member private constructor(
    val name: String,
    val email: String,
) {
    companion object {
        fun create(
            name: String,
            email: String,
        ): Member {
            require(name.isNotBlank()) {
                "이름은 필수입니다."
            }

            require(email.contains("@")) {
                "이메일 형식이 올바르지 않습니다."
            }

            return Member(
                name = name,
                email = email,
            )
        }
    }
}
```

Service에서 생성합니다.

```kotlin
val member = Member.create(
    name = request.name,
    email = request.email,
)
```

Kotlin은 named argument와 data class가 있어 단순 매핑 코드가 비교적 읽기 쉽습니다. 따라서 단순 변환이라면 별도 Mapper 없이 DTO의 `from`을 사용하는 경우가 많습니다.

## 실무 권장 기준

### 소규모 CRUD 프로젝트

```
Entity → Response DTO
DTO.from(entity)

Request DTO → Entity
request.toEntity()
```

간단하고 생산성이 높습니다.

### 도메인 규칙이 있는 프로젝트

```
Entity → Response DTO
DTO.from(entity)

Request DTO → Entity
Service에서 Entity.create(...) 호출
```

Request DTO가 도메인 생성 규칙을 직접 알지 않도록 합니다.

### 복잡한 엔터프라이즈 프로젝트

```
Entity → Response DTO
Mapper 사용

Request DTO → Command 또는 도메인 입력 객체
Mapper 또는 Application Service 사용
```

변환 로직을 명시적으로 분리합니다.

## 추천 구조

대부분의 Spring Boot 프로젝트에서는 다음 구조가 균형이 좋습니다.

```java
public record CreateMemberRequest(
    String name,
    String email
) {
}
```

```java
public record MemberResponse(
    Long id,
    String name,
    String email
) {

    public static MemberResponse from(Member member) {
        return new MemberResponse(
            member.getId(),
            member.getName(),
            member.getEmail()
        );
    }
}
```

```java
@Transactional
public MemberResponse createMember(
    CreateMemberRequest request
) {
    Member member = Member.create(
        request.name(),
        request.email()
    );

    Member savedMember = memberRepository.save(member);

    return MemberResponse.from(savedMember);
}
```

각 책임은 다음과 같이 나뉩니다.

```
Request DTO
입력값 전달

Service
유스케이스 흐름 조정

Entity
생성 규칙과 도메인 검증

Response DTO
응답 형태로 변환
```

## 전체 요약

DTO 변환 책임은 변환 방향과 복잡도에 따라 결정하는 것이 좋습니다.

```
Entity → Response DTO
Response DTO의 from 메서드 권장

Request DTO → Entity
단순 CRUD는 toEntity 가능
도메인 규칙이 있으면 Service에서 Entity.create 호출

복잡한 변환
별도 Mapper 클래스 사용
```

Entity에 `toResponse()`를 두면 도메인 계층이 API DTO에 의존하게 되므로 일반적으로 권장하지 않습니다.

가장 실용적인 기준은 다음과 같습니다.

```java
MemberResponse.from(member);

Member member = Member.create(
    request.name(),
    request.email()
);
```

변환 로직이 복잡해지는 시점에 Mapper로 분리하면 됩니다.

# DTO 또는 Entity를 응답 객체로 변환하는 위치

## 결론

`DTO 또는 Entity → Response 객체` 변환은 보통 `"Response 클래스 내부"` 또는 `"별도 Mapper"`에 두는 것이 좋습니다.

가장 일반적인 형태는 다음입니다.

```java
MemberResponse.from(member);
```

즉, `"결과 타입이 원본을 받아 자신을 생성"`하도록 합니다.

---

## Entity → Response

Response 객체 내부에 `from()`을 두는 방식이 가장 무난합니다.

```java
public record MemberResponse(
    Long id,
    String name,
    String email
) {
    public static MemberResponse from(Member member) {
        return new MemberResponse(
            member.getId(),
            member.getName(),
            member.getEmail()
        );
    }
}
```

서비스에서는 다음과 같이 사용합니다.

```java
public MemberResponse findMember(Long memberId) {
    Member member = memberRepository.findById(memberId)
        .orElseThrow();

    return MemberResponse.from(member);
}
```

의존성 방향은 다음과 같습니다.

```
Response DTO → Entity
Entity → Response DTO 의존 없음
```

Entity에 `toResponse()`를 두면 Entity가 API 응답 구조를 알게 되므로 일반적으로 피하는 편이 좋습니다.

```java
// 권장하지 않음
member.toResponse();
```

---

## 조회 DTO → Response

Repository나 QueryDSL에서 조회 전용 DTO를 반환하고, 이를 API 응답 객체로 변환하는 경우도 Response 내부에 둘 수 있습니다.

```java
public record MemberQueryDto(
    Long id,
    String name,
    long orderCount
) {
}
```

```java
public record MemberResponse(
    Long id,
    String name,
    long orderCount
) {
    public static MemberResponse from(MemberQueryDto dto) {
        return new MemberResponse(
            dto.id(),
            dto.name(),
            dto.orderCount()
        );
    }
}
```

```java
MemberQueryDto result = memberQueryRepository.findMember(memberId);

return MemberResponse.from(result);
```

이 구조는 API Response와 내부 조회 모델을 분리할 때 유용합니다.

---

## 이미 응답 DTO라면 변환하지 않아도 됨

Repository나 Service가 반환하는 DTO 자체가 API 응답 모델이라면 추가 Response 객체를 만들 필요가 없습니다.

```java
public record MemberResponse(
    Long id,
    String name,
    long orderCount
) {
}
```

```java
public MemberResponse findMember(Long memberId) {
    return memberQueryRepository.findMemberResponse(memberId);
}
```

다만 이 경우 조회 계층이 API 응답 타입에 직접 의존합니다.

단순 CRUD나 작은 프로젝트에서는 괜찮지만, 다음 상황에서는 조회 DTO와 Response DTO를 분리하는 것이 좋습니다.

- 같은 조회 결과를 여러 API에서 다르게 표현할 때
- API 버전별 응답 구조가 다를 때
- 내부 조회 모델이 자주 변경될 때
- 표현 계층과 조회 계층을 엄격히 분리할 때

---

## Mapper를 사용하는 경우

여러 객체를 조합하거나 변환이 복잡하면 Response 내부의 `from()`보다 별도 Mapper가 적합합니다.

```java
@Component
public class MemberResponseMapper {

    public MemberResponse toResponse(
        Member member,
        List<Order> orders
    ) {
        return new MemberResponse(
            member.getId(),
            member.getName(),
            orders.size()
        );
    }
}
```

```java
return memberResponseMapper.toResponse(member, orders);
```

다음과 같은 경우 Mapper 분리를 고려하면 됩니다.

- 여러 Entity 또는 DTO를 조합함
- 조건에 따라 필드 값이 달라짐
- 중첩 Response 변환이 많음
- 날짜, 금액, 상태 포맷팅이 복잡함
- 동일한 변환을 여러 곳에서 재사용함

---

## Controller에서 변환하는 것은 어떤가

Controller에서 다음처럼 변환할 수도 있습니다.

```java
@GetMapping("/{id}")
public MemberResponse findMember(@PathVariable Long id) {
    Member member = memberService.findMember(id);

    return MemberResponse.from(member);
}
```

기술적으로 문제는 없지만, Service가 Entity를 Controller까지 노출하게 됩니다.

이 경우 다음 문제가 생길 수 있습니다.

- Controller가 도메인 객체 구조를 알아야 함
- 지연 로딩 문제가 트랜잭션 밖으로 노출될 수 있음
- 여러 Controller에서 변환 코드가 반복될 수 있음
- 응답 생성에 필요한 조회가 Controller에 추가될 수 있음

따라서 일반적으로 Service 또는 Application 계층에서 Response 변환까지 마치고 반환하는 편이 안전합니다.

```java
public MemberResponse findMember(Long id) {
    Member member = memberRepository.findById(id)
        .orElseThrow();

    return MemberResponse.from(member);
}
```

## 패키지 구조 예시

```
member
├── controller
│   └── MemberController
├── service
│   └── MemberService
├── domain
│   └── Member
└── dto
    ├── request
    │   └── CreateMemberRequest
    ├── response
    │   └── MemberResponse
    └── query
        └── MemberQueryDto
```

변환 코드는 다음처럼 위치시킬 수 있습니다.

```
Entity → Response
MemberResponse.from(member)

Query DTO → Response
MemberResponse.from(queryDto)

복잡한 조합
MemberResponseMapper.toResponse(...)
```

## 추천 기준

### 단순 Entity 변환

```java
MemberResponse.from(member);
```

Response 객체 내부가 좋습니다.

### 단순 조회 DTO 변환

```java
MemberResponse.from(memberQueryDto);
```

Response 객체 내부가 좋습니다.

### 복잡한 변환

```java
memberResponseMapper.toResponse(...);
```

별도 Mapper가 좋습니다.

### Entity 내부 변환

```java
member.toResponse();
```

도메인이 API 응답 타입에 의존하므로 가급적 피합니다.

## 전체 요약

```
Entity → Response
Response.from(entity)

조회 DTO → Response
Response.from(dto)

여러 객체 조합 또는 복잡한 변환
별도 Mapper

Entity.toResponse()
일반적으로 비권장

변환 실행 위치
Service 또는 Application 계층
```

핵심은 `"응답 객체가 원본 객체를 알게 하고, Entity는 응답 객체를 모르게 하는 것"`입니다.
