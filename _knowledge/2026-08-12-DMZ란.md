## 개요

인프라에서 "DMZ(Demilitarized Zone, 비무장지대)"란 인터넷과 내부 사설망 사이에 별도로 구성하는 중간 네트워크 영역입니다.

외부 사용자가 접근해야 하는 서버를 내부망에 직접 배치하지 않고 DMZ에 배치하여, 외부 공격이 발생하더라도 내부 시스템까지 바로 침투하기 어렵도록 만드는 보안 구조입니다.

쉽게 표현하면 다음과 같습니다.

```
인터넷
  ↓
DMZ
  ↓
내부망
```

DMZ는 외부망과 내부망 사이의 "완충 지대" 역할을 합니다.

---

## DMZ가 필요한 이유

외부에서 접근 가능한 웹 서버를 내부망에 그대로 배치하면, 웹 서버가 공격당했을 때 내부 데이터베이스나 사내 시스템까지 연결될 가능성이 높아집니다.

DMZ를 구성하면 외부에서 접근할 수 있는 범위를 DMZ 내부 서버로 제한할 수 있습니다.

```
인터넷 → 웹 서버 접근 가능
인터넷 → 내부 DB 접근 불가능
웹 서버 → 필요한 DB 포트만 접근 가능
```

즉, DMZ의 핵심 목적은 다음과 같습니다.

- 외부 공개 서버와 내부 시스템 분리
- 침해 사고 발생 시 피해 범위 제한
- 네트워크 접근 경로 통제
- 방화벽 정책을 통한 최소 권한 적용
- 내부 데이터베이스와 관리 시스템 보호

---

## 일반적인 DMZ 구성

### 기본 구성

```
[인터넷]
    ↓
[외부 방화벽]
    ↓
[DMZ]
    ↓
[내부 방화벽]
    ↓
[내부망]
```

DMZ에는 외부에서 접근해야 하는 서버를 배치합니다.

```
DMZ
├─ 웹 서버
├─ 리버스 프록시
├─ 로드밸런서
├─ API Gateway
├─ 메일 서버
├─ DNS 서버
└─ VPN Gateway
```

내부망에는 외부에서 직접 접근하면 안 되는 시스템을 배치합니다.

```
내부망
├─ 데이터베이스
├─ 애플리케이션 서버
├─ 사내 업무 시스템
├─ 파일 서버
├─ Kubernetes Worker Node
└─ 관리 서버
```

---

## DMZ의 접근 제어 방식

DMZ를 구성했다고 해서 DMZ 서버가 내부망에 자유롭게 접근할 수 있는 것은 아닙니다.

방화벽이나 보안 그룹을 통해 필요한 통신만 허용해야 합니다.

예를 들어 웹 서버와 데이터베이스 구조라면 다음과 같이 구성할 수 있습니다.

```
인터넷
  │
  │ TCP 443 허용
  ▼
DMZ 웹 서버
  │
  │ TCP 3306 허용
  ▼
내부망 MySQL
```

허용 정책은 다음과 같습니다.

| 출발지 | 목적지 | 포트 | 허용 여부 |
| --- | --- | --- | --- |
| 인터넷 | DMZ 웹 서버 | 443 | 허용 |
| 인터넷 | 내부 DB | 3306 | 차단 |
| DMZ 웹 서버 | 내부 DB | 3306 | 허용 |
| DMZ 웹 서버 | 내부 전체망 | 전체 | 차단 |
| 관리자 PC | Bastion | 22 | 제한적으로 허용 |

DMZ 서버에서 내부망으로 들어가는 통신도 반드시 필요한 대상과 포트만 허용하는 것이 중요합니다.

## 클라우드 환경에서의 DMZ

클라우드에서는 반드시 "DMZ"라는 이름의 별도 기능이 존재하는 것은 아닙니다.

일반적으로 Public Subnet이 DMZ 역할을 수행합니다.

```
VPC
├─ Public Subnet
│   ├─ Public Load Balancer
│   ├─ Bastion Host
│   └─ NAT Gateway
│
└─ Private Subnet
    ├─ Kubernetes Node
    ├─ Application Server
    └─ Database
```

이 구조에서는 다음과 같이 볼 수 있습니다.

```
Public Subnet ≈ DMZ
Private Subnet ≈ 내부망
```

다만 Public Subnet에 있다고 해서 자동으로 DMZ가 되는 것은 아닙니다.

다음 조건이 함께 적용되어야 합니다.

- 인터넷 게이트웨이 연결
- Public IP 또는 Public Load Balancer 사용
- Security Group 또는 ACG 설정
- Network ACL 설정
- 내부망 접근 최소화
- 관리 포트 접근 제한

---

## Kubernetes 환경에서의 DMZ

Kubernetes 환경에서는 일반적으로 Kubernetes 노드나 데이터베이스를 DMZ에 직접 배치하지 않습니다.

권장 구조는 다음과 같습니다.

```
인터넷
  ↓
Public Load Balancer
  ↓
Ingress Controller
  ↓
Kubernetes Service
  ↓
Pod
  ↓
Database
```

네트워크 영역으로 표현하면 다음과 같습니다.

```
Public Subnet
└─ Public Load Balancer

Private Subnet
├─ Kubernetes Control Plane 또는 Worker Node
├─ Ingress Controller
├─ Application Pod
└─ Database
```

외부에 공개되는 것은 Load Balancer뿐이며, Kubernetes 노드와 데이터베이스는 Private Subnet에 배치합니다.

### API Gateway를 사용하는 경우

```
인터넷
  ↓
Public Load Balancer
  ↓
API Gateway
  ↓
내부 API
  ↓
Database
```

API Gateway 자체를 Public Subnet에 직접 배치할 수도 있지만, 클라우드 Kubernetes 환경에서는 Public Load Balancer만 외부에 노출하고 API Gateway Pod는 Private Subnet의 Kubernetes 내부에 배치하는 방식이 일반적입니다.

## Bastion Host와 DMZ

Bastion Host는 외부 관리자가 내부 서버에 접속할 때 사용하는 중계 서버입니다.

```
관리자 PC
  ↓ SSH
Bastion Host
  ↓ SSH 또는 터널링
내부 서버
```

Bastion은 외부 접근이 필요하기 때문에 DMZ 또는 Public Subnet에 배치되는 경우가 많습니다.

다만 다음과 같이 강하게 제한해야 합니다.

- 회사 IP에서만 SSH 허용
- SSH Key 인증 사용
- 비밀번호 로그인 차단
- Root 로그인 차단
- 접속 로그 기록
- 필요한 내부 서버로만 접근 허용
- DB는 Bastion 터널링을 통해 접근

Bastion은 외부에 노출된 관리 진입점이기 때문에 일반 웹 서버보다 더 엄격한 보안 설정이 필요합니다.

---

## DMZ와 Public Subnet의 차이

DMZ와 Public Subnet은 비슷하게 사용되지만 정확히 같은 개념은 아닙니다.

| 구분 | DMZ | Public Subnet |
| --- | --- | --- |
| 의미 | 보안을 위한 중간 네트워크 영역 | 인터넷 연결 경로가 있는 서브넷 |
| 관점 | 보안 아키텍처 | 네트워크 구성 |
| 구현 방식 | 방화벽, ACL, 라우팅, 망 분리 | Route Table, Internet Gateway |
| 내부망 통제 | 핵심 요소 | 별도 보안 정책 필요 |
| 클라우드 사용 | Public Subnet으로 구현 가능 | 반드시 DMZ 역할을 하는 것은 아님 |

즉, Public Subnet은 네트워크 기술적인 구분이고, DMZ는 보안 목적의 아키텍처 개념입니다.

Public Subnet에 서버를 배치하면서 내부망 접근을 엄격히 통제하면 DMZ 역할을 수행할 수 있습니다.

## 대표적인 잘못된 구성

### 모든 서버를 Public Subnet에 배치

```
Public Subnet
├─ 웹 서버
├─ API 서버
├─ Kubernetes Node
└─ Database
```

모든 서버가 인터넷에 노출될 가능성이 있기 때문에 위험합니다.

### DMZ에서 내부망 전체 접근 허용

```
DMZ → 내부망 전체 포트 허용
```

DMZ 서버가 해킹되면 내부망 전체로 공격이 확산될 수 있습니다.

### Bastion SSH를 전체 인터넷에 공개

```
0.0.0.0/0 → Bastion TCP 22 허용
```

SSH 스캐닝과 무차별 대입 공격의 대상이 될 수 있습니다.

### 데이터베이스를 외부에 직접 공개

```
인터넷 → MySQL 3306
```

애플리케이션 서버를 거치지 않고 데이터베이스가 직접 공격받을 수 있으므로 피해야 합니다.

## 권장 구성 예시

```
인터넷
  ↓ HTTPS 443
Public Load Balancer
  ↓
Private Kubernetes Cluster
  ↓
Application Pod
  ↓
Private Database
```

관리 경로는 별도로 구성합니다.

```
회사 내부 네트워크
  ↓ SSH 22
Bastion Host
  ↓
Kubernetes / Database / 내부 서버
```

보안 정책은 다음과 같이 적용합니다.

```
인터넷 → Load Balancer: 443 허용
인터넷 → Bastion: 차단
회사 IP → Bastion: 22 허용
인터넷 → Kubernetes Node: 차단
인터넷 → Database: 차단
Application → Database: DB 포트만 허용
Bastion → 내부 관리 포트: 필요한 범위만 허용
```

## 전체 요약

DMZ는 인터넷과 내부망 사이에 구성하는 보안 완충 영역입니다.

외부에서 접근해야 하는 Load Balancer, 웹 서버, Bastion 등의 시스템을 DMZ에 배치하고, 데이터베이스나 Kubernetes 노드 같은 중요 시스템은 내부망에 배치합니다.

클라우드에서는 일반적으로 다음과 같이 구현합니다.

```
Public Subnet = 외부 진입 영역
Private Subnet = 내부 시스템 영역
```

그러나 Public Subnet 자체가 DMZ를 의미하는 것은 아니며, 방화벽, ACG, Security Group, ACL, 라우팅과 내부망 접근 제한을 함께 적용해야 실제 DMZ 역할을 수행합니다.
