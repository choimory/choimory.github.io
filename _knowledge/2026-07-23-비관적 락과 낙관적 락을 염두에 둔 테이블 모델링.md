## 개요

동시성 제어를 염두에 둔 테이블 모델링의 핵심은 "데이터 충돌이 어디서 발생하는지"를 먼저 식별하는 것입니다.

비관적 락과 낙관적 락은 단순히 SQL 옵션만의 문제가 아니라, 테이블 구조, 컬럼 설계, 트랜잭션 범위, 인덱스, 상태값 모델링까지 함께 고려해야 합니다.

간단히 말하면 다음과 같습니다.

| 구분 | 핵심 관점 | 대표 방식 |
| --- | --- | --- |
| 비관적 락 | 충돌이 날 것이라고 보고 먼저 잠금 | `SELECT ... FOR UPDATE` |
| 낙관적 락 | 충돌은 드물다고 보고 수정 시점에 검증 | `version`, `updated_at` 조건 비교 |
| 테이블 모델링 핵심 | 어떤 행을 잠글지, 어떤 값으로 충돌을 감지할지 결정 | PK, 상태 컬럼, version 컬럼, unique 제약 |

---

## 비관적 락을 염두에 둔 테이블 모델링

비관적 락은 "수정 대상 row를 먼저 잡고, 다른 트랜잭션이 못 건드리게 막는 방식"입니다.

예를 들어 재고 차감, 좌석 예약, 쿠폰 선착순 발급처럼 동시에 같은 데이터를 건드릴 가능성이 높은 곳에 적합합니다.

---

## 기본 테이블 예시

```sql
CREATE TABLE product_stock (
    product_id BIGINT PRIMARY KEY,
    quantity INT NOT NULL,
    reserved_quantity INT NOT NULL DEFAULT 0,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

재고 차감 시에는 다음처럼 특정 상품 row를 잠급니다.

```sql
START TRANSACTION;

SELECT product_id, quantity
FROM product_stock
WHERE product_id = 1
FOR UPDATE;

UPDATE product_stock
SET quantity = quantity - 1
WHERE product_id = 1
  AND quantity >= 1;

COMMIT;
```

여기서 중요한 점은 "잠금 대상 row가 명확해야 한다"는 것입니다.

즉, 비관적 락을 잘 쓰려면 다음 조건이 필요합니다.

| 모델링 요소 | 이유 |
| --- | --- |
| 명확한 PK | 정확히 한 row를 잠그기 위해 필요 |
| 적절한 인덱스 | 불필요한 범위 락을 줄이기 위해 필요 |
| 상태 컬럼 | 예약 가능, 처리 중, 완료 등의 흐름 제어 |
| 트랜잭션 범위 최소화 | 락 점유 시간을 줄이기 위해 필요 |

---

## 비관적 락에서 중요한 인덱스 설계

비관적 락에서는 인덱스가 매우 중요합니다.

MySQL InnoDB 기준으로, 조건에 맞는 인덱스를 제대로 타지 못하면 의도보다 넓은 범위가 잠길 수 있습니다.

예를 들어 예약 테이블이 있다고 해보겠습니다.

```sql
CREATE TABLE reservation_seat (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id BIGINT NOT NULL,
    seat_no VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL,
    user_id BIGINT NULL,
    reserved_at DATETIME NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_event_seat (event_id, seat_no),
    INDEX idx_event_status (event_id, status)
);
```

좌석 하나를 예약할 때는 다음처럼 `event_id + seat_no`로 정확히 하나의 row를 잡는 구조가 좋습니다.

```sql
START TRANSACTION;

SELECT id, status
FROM reservation_seat
WHERE event_id = 100
  AND seat_no = 'A-1'
FOR UPDATE;

UPDATE reservation_seat
SET status = 'RESERVED',
    user_id = 10,
    reserved_at = NOW()
WHERE event_id = 100
  AND seat_no = 'A-1'
  AND status = 'AVAILABLE';

COMMIT;
```

이 구조에서 `UNIQUE KEY uk_event_seat (event_id, seat_no)`가 중요한 이유는, 좌석 하나가 정확히 하나의 row로 식별되기 때문입니다.

## 비관적 락에 적합한 모델링 패턴

### 1. 단일 자원 row 잠금

재고, 포인트, 계좌 잔액처럼 하나의 row가 하나의 자원을 대표하는 구조입니다.

```sql
CREATE TABLE account_balance (
    account_id BIGINT PRIMARY KEY,
    balance DECIMAL(15, 2) NOT NULL,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

```sql
SELECT balance
FROM account_balance
WHERE account_id = 1
FOR UPDATE;
```

이 패턴은 단순하고 강력하지만, 특정 row에 트래픽이 몰리면 병목이 생깁니다.

---

### 2. 상태 기반 선점

작업 큐, 주문 처리, 배치 작업 등에 적합합니다.

```sql
CREATE TABLE job_queue (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    status VARCHAR(20) NOT NULL,
    payload JSON NOT NULL,
    locked_by VARCHAR(100) NULL,
    locked_at DATETIME NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_status_created_at (status, created_at)
);
```

작업자가 하나의 작업을 가져갈 때:

```sql
START TRANSACTION;

SELECT id
FROM job_queue
WHERE status = 'READY'
ORDER BY created_at
LIMIT 1
FOR UPDATE;

UPDATE job_queue
SET status = 'PROCESSING',
    locked_by = 'worker-1',
    locked_at = NOW()
WHERE id = 1;

COMMIT;
```

MySQL 8 이상에서는 상황에 따라 `SKIP LOCKED`도 사용할 수 있습니다.

```sql
SELECT id
FROM job_queue
WHERE status = 'READY'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

이렇게 하면 이미 다른 트랜잭션이 잡은 row는 건너뛰고 다음 작업을 가져올 수 있습니다.

## 낙관적 락을 염두에 둔 테이블 모델링

낙관적 락은 "읽을 때는 잠그지 않고, 수정할 때 내가 읽은 버전이 아직 유효한지 검사하는 방식"입니다.

주로 충돌 가능성은 있지만 빈번하지 않은 데이터에 적합합니다.

예를 들어 게시글 수정, 회원 프로필 수정, 상품 정보 수정, 주문 상태 변경 등에 많이 사용합니다.

---

## 기본 테이블 예시

```sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(15, 2) NOT NULL,
    stock_quantity INT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

수정 시에는 `id`와 `version`을 함께 조건에 넣습니다.

```sql
UPDATE product
SET name = '수정된 상품명',
    price = 12000,
    version = version + 1,
    updated_at = NOW()
WHERE id = 1
  AND version = 3;
```

이때 업데이트된 row 수가 `0`이면 다른 트랜잭션이 먼저 수정한 것입니다.

즉, 애플리케이션에서는 다음처럼 판단합니다.

| 결과 | 의미 |
| --- | --- |
| affected rows = 1 | 수정 성공 |
| affected rows = 0 | 충돌 발생, 재조회 또는 실패 처리 필요 |

---

## 낙관적 락용 컬럼 설계

낙관적 락에서는 보통 `version` 컬럼을 둡니다.

```sql
version BIGINT NOT NULL DEFAULT 0
```

`updated_at`으로도 비슷하게 할 수 있지만, 일반적으로는 `version`이 더 명확합니다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| `version` | 충돌 검출 목적이 명확함 | 컬럼 추가 필요 |
| `updated_at` | 이미 있는 컬럼 활용 가능 | 정밀도 문제, 자동 갱신 정책 혼동 가능 |
| checksum/hash | 여러 컬럼 변경 감지 가능 | 구현 복잡도 높음 |

권장 방식은 `version`입니다.

---

## 낙관적 락에 적합한 모델링 패턴

### 1. 일반 엔티티 수정

```sql
CREATE TABLE article (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

수정:

```sql
UPDATE article
SET title = '새 제목',
    content = '새 내용',
    version = version + 1,
    updated_at = NOW()
WHERE id = 1
  AND version = 5;
```

동시에 두 사용자가 같은 게시글을 수정하면, 먼저 저장한 쪽만 성공하고 나중에 저장한 쪽은 충돌을 감지할 수 있습니다.

---

### 2. 상태 전이 검증

주문 같은 데이터는 단순 version뿐 아니라 "현재 상태가 기대한 상태인지"도 같이 검증하는 것이 좋습니다.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount DECIMAL(15, 2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_user_id (user_id),
    INDEX idx_status (status)
);
```

결제 완료 처리:

```sql
UPDATE orders
SET status = 'PAID',
    version = version + 1,
    updated_at = NOW()
WHERE id = 1
  AND status = 'PENDING'
  AND version = 2;
```

이렇게 하면 다음 두 가지를 동시에 보장합니다.

| 조건 | 역할 |
| --- | --- |
| `status = 'PENDING'` | 올바른 상태에서만 변경 |
| `version = 2` | 중간에 다른 수정이 없었는지 확인 |

## 비관적 락과 낙관적 락을 모두 고려한 테이블 모델링

실무에서는 한 시스템 안에서도 두 방식을 함께 씁니다.

예를 들어 주문 시스템을 보면:

| 도메인 | 적합한 락 |
| --- | --- |
| 상품 재고 차감 | 비관적 락 또는 원자적 UPDATE |
| 주문 정보 수정 | 낙관적 락 |
| 결제 상태 변경 | 낙관적 락 + 상태 조건 |
| 쿠폰 선착순 발급 | 비관적 락 또는 unique 제약 |
| 관리자 상품 정보 수정 | 낙관적 락 |

---

## 예시: 주문과 재고 테이블

```sql
CREATE TABLE product_stock (
    product_id BIGINT PRIMARY KEY,
    quantity INT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount DECIMAL(15, 2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_user_status (user_id, status)
);

CREATE TABLE order_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    price DECIMAL(15, 2) NOT NULL,

    INDEX idx_order_id (order_id),
    INDEX idx_product_id (product_id)
);
```

여기서 재고는 충돌 가능성이 높으므로 다음처럼 처리할 수 있습니다.

```sql
UPDATE product_stock
SET quantity = quantity - 1,
    version = version + 1,
    updated_at = NOW()
WHERE product_id = 1
  AND quantity >= 1;
```

이 방식은 `SELECT ... FOR UPDATE`를 직접 쓰지 않아도, `UPDATE` 자체가 row lock을 잡기 때문에 재고 차감에서는 자주 사용됩니다.

주문 상태 변경은 낙관적 락으로 처리합니다.

```sql
UPDATE orders
SET status = 'PAID',
    version = version + 1,
    updated_at = NOW()
WHERE id = 100
  AND status = 'PENDING'
  AND version = 3;
```

## Unique 제약을 이용한 동시성 제어

락만으로 해결하려 하지 말고, DB 제약 조건도 함께 설계하는 것이 좋습니다.

예를 들어 사용자당 쿠폰 1회 발급이라면 다음처럼 모델링합니다.

```sql
CREATE TABLE user_coupon (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NOT NULL,
    issued_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_user_coupon (user_id, coupon_id)
);
```

동시에 여러 요청이 들어와도 `UNIQUE KEY`가 중복 발급을 막아줍니다.

```sql
INSERT INTO user_coupon (user_id, coupon_id)
VALUES (1, 100);
```

중복 발급 시도는 DB 에러가 나고, 애플리케이션에서 "이미 발급됨"으로 처리하면 됩니다.

이런 구조는 락보다 더 단단합니다.

## 상태 컬럼 모델링

동시성 제어가 필요한 테이블은 상태 컬럼을 대충 두면 안 됩니다.

예를 들어 주문 상태는 다음처럼 명확한 흐름을 가져야 합니다.

```
PENDING -> PAID -> PREPARING -> SHIPPED -> DELIVERED
PENDING -> CANCELED
PAID -> REFUNDED
```

테이블:

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

상태 변경:

```sql
UPDATE orders
SET status = 'CANCELED',
    version = version + 1,
    updated_at = NOW()
WHERE id = 1
  AND status = 'PENDING'
  AND version = 4;
```

이렇게 하면 이미 결제된 주문을 뒤늦게 취소하는 문제를 막을 수 있습니다.

즉, 상태 컬럼은 단순 표시용이 아니라 "동시성 제어 조건"으로도 사용됩니다.

---

## 락을 고려한 테이블 설계 체크리스트

| 항목 | 설명 |
| --- | --- |
| PK가 명확한가 | 하나의 row를 정확히 식별할 수 있어야 합니다 |
| 동시 수정 가능성이 높은 컬럼이 무엇인가 | 재고, 잔액, 상태, 카운트 등이 대표적입니다 |
| `version` 컬럼이 필요한가 | 낙관적 락 대상이면 거의 필요합니다 |
| 상태 전이 조건이 있는가 | `PENDING -> PAID` 같은 흐름을 SQL 조건에 넣어야 합니다 |
| unique 제약으로 막을 수 있는가 | 중복 예약, 중복 발급은 unique로 막는 것이 좋습니다 |
| 인덱스가 락 범위를 줄이는가 | 비관적 락에서는 특히 중요합니다 |
| 트랜잭션이 너무 길지 않은가 | 외부 API 호출을 락 안에서 하면 위험합니다 |
| hot row가 생기지 않는가 | 한 row에 요청이 몰리면 병목이 됩니다 |

---

## 상황별 추천 설계

| 상황 | 추천 방식 |
| --- | --- |
| 게시글 수정 | `version` 기반 낙관적 락 |
| 상품 정보 수정 | `version` 기반 낙관적 락 |
| 주문 상태 변경 | `status + version` 조건 |
| 재고 차감 | 원자적 `UPDATE` 또는 비관적 락 |
| 좌석 예약 | unique 제약 + 비관적 락 |
| 쿠폰 발급 | unique 제약 + 원자적 INSERT |
| 계좌 이체 | 비관적 락 + 트랜잭션 |
| 작업 큐 | `FOR UPDATE SKIP LOCKED` |
| 좋아요 중복 방지 | unique 제약 |
| 조회수 증가 | 별도 카운터 테이블 또는 비동기 집계 |

## 실무적으로 추천하는 기본 컬럼

동시성 제어가 필요한 주요 도메인 테이블에는 기본적으로 다음 컬럼을 두는 것이 좋습니다.

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT,
version BIGINT NOT NULL DEFAULT 0,
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

상태 기반 엔티티라면 다음도 추가합니다.

```sql
status VARCHAR(30) NOT NULL
```

중복 생성이 문제라면 unique 제약을 추가합니다.

```sql
UNIQUE KEY uk_domain_rule (...)
```

예를 들어 주문 테이블은 다음 정도가 기본형입니다.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount DECIMAL(15, 2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_user_id (user_id),
    INDEX idx_status (status)
);
```

## 주의할 점

### 1. 낙관적 락은 충돌을 막는 것이 아니라 감지하는 방식입니다

낙관적 락은 동시에 수정하는 것을 물리적으로 막지 않습니다.

대신 저장 시점에 `version`이 달라졌는지 확인해서 충돌을 감지합니다.

그래서 충돌 발생 시 정책이 필요합니다.

| 충돌 발생 시 처리 | 설명 |
| --- | --- |
| 사용자에게 재시도 요청 | 게시글, 설정 변경 등에 적합 |
| 자동 재조회 후 재시도 | 단순 카운트, 누적값 등에 가능 |
| 실패 처리 | 선착순 이벤트 등에 적합 |

---

### 2. 비관적 락은 트랜잭션을 짧게 잡아야 합니다

비관적 락을 사용할 때는 트랜잭션 안에서 오래 걸리는 일을 하면 안 됩니다.

피해야 할 예시는 다음과 같습니다.

```
트랜잭션 시작
row lock 획득
외부 결제 API 호출
이메일 발송
파일 업로드
트랜잭션 커밋
```

이렇게 하면 락을 잡은 채로 외부 시스템 응답을 기다리기 때문에 병목과 데드락 가능성이 커집니다.

좋은 방식은 다음과 같습니다.

```
트랜잭션 시작
필요한 DB 상태 변경
트랜잭션 커밋
외부 API 호출 또는 이벤트 발행
```

또는 아웃박스 패턴을 사용합니다.

---

### 3. 락보다 제약 조건이 더 안전할 때가 많습니다

중복 생성 문제는 락보다 unique 제약이 더 확실합니다.

예를 들어 "한 유저가 한 게시글에 좋아요 한 번만 가능"은 다음처럼 처리하는 것이 좋습니다.

```sql
CREATE TABLE post_like (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    post_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_post_user (post_id, user_id)
);
```

이 경우 동시에 좋아요 요청이 두 번 들어와도 DB가 중복을 막아줍니다.

---

## 전체 요약

비관적 락과 낙관적 락을 염두에 둔 테이블 모델링의 핵심은 다음과 같습니다.

| 핵심 | 설명 |
| --- | --- |
| 비관적 락 | 충돌 가능성이 높은 row를 먼저 잠그는 방식입니다 |
| 낙관적 락 | `version`으로 수정 시점의 충돌을 감지하는 방식입니다 |
| 비관적 락 모델링 | PK, 인덱스, 상태 컬럼, 짧은 트랜잭션이 중요합니다 |
| 낙관적 락 모델링 | `version` 컬럼과 `WHERE id = ? AND version = ?` 조건이 중요합니다 |
| 상태 변경 | `status + version` 조건을 함께 쓰는 것이 좋습니다 |
| 중복 방지 | 락보다 `UNIQUE KEY`가 더 안전한 경우가 많습니다 |
| 재고 차감 | 원자적 `UPDATE` 또는 `FOR UPDATE`를 사용합니다 |
| 실무 기본값 | 주요 테이블에 `version`, `created_at`, `updated_at`, 필요 시 `status`를 둡니다 |

결론적으로, 테이블 모델링 단계에서 다음 세 가지를 미리 정해야 합니다.

```
1. 어떤 row가 동시에 수정될 수 있는가
2. 충돌을 잠금으로 막을 것인가, version으로 감지할 것인가
3. unique 제약이나 상태 조건으로 DB 레벨에서 막을 수 있는가
```

이 세 가지를 기준으로 설계하면 비관적 락과 낙관적 락을 모두 고려한 안정적인 테이블 구조를 만들 수 있습니다.
