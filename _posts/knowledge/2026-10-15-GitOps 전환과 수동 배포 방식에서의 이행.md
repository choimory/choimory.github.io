## 개요
GitOps는 시스템의 원하는 상태를 Git에 선언적으로 저장하고, 에이전트가 이 상태와 실제 환경을 지속적으로 비교해 일치시키는 운영 모델입니다. 수동 배포(스크립트 실행, 콘솔 조작, 직접 `kubectl apply`)에서 전환하면 변경 이력의 추적성, 환경 재현성, 롤백의 단순성, 권한 관리의 안전성이 크게 향상됩니다.
전환은 한 번에 갈아엎는 것이 아니라 기존 방식과 병행하며 점진적으로 이관하는 과정이며, 시크릿 관리와 환경 구조, 팀의 워크플로 변화까지 함께 설계해야 성공합니다. 이 문서는 GitOps의 원칙과 구조, 수동 방식과의 차이, 단계적 이행 방법을 다룹니다.
---
## 수동 배포의 문제와 GitOps의 접근
### 수동 방식의 한계
CI 서버가 `kubectl apply`나 배포 스크립트를 실행하는 push 방식은 클러스터 자격증명을 CI 시스템이 보관해야 하고, 누군가 클러스터를 직접 수정하면 Git과 실제 상태가 어긋나도 알 수 없습니다. 누가 언제 무엇을 바꿨는지는 배포 로그를 뒤져야 알 수 있으며, 클러스터를 새로 만들어야 할 때 현재 상태를 그대로 복원하기 어렵습니다.
### GitOps의 네 가지 원칙
선언적 기술(원하는 상태만 기술), Git을 단일 진실 공급원으로 사용한 버전 관리와 불변성, 승인된 변경의 자동 적용, 소프트웨어 에이전트에 의한 지속적 상태 조정(reconciliation)입니다. 개발자는 클러스터에 직접 접근하지 않고 Git에 PR을 올리며, 변경은 리뷰와 승인을 거쳐 반영됩니다.

| 항목 | 수동 / Push 배포 | GitOps (Pull) |
| --- | --- | --- |
| 클러스터 자격증명 | CI가 보관 | 클러스터 내부 에이전트만 보유 |
| 드리프트 감지 | 불가능 | 지속 비교 후 알림 또는 자동 복원 |
| 변경 이력 | 배포 로그 | Git 커밋과 PR |
| 롤백 | 이전 스크립트 재실행 | Git 리버트 |
| 환경 복원 | 어려움 | Git에서 재적용 |

### Pull 방식의 보안 이점
`ArgoCD`나 `Flux`는 클러스터 안에서 Git을 주기적으로 가져와(pull) 적용하므로 CI가 클러스터에 접근할 필요가 없습니다. CI가 침해되어도 클러스터 자격증명이 유출되지 않으며, 클러스터 접근 경로가 하나로 줄어듭니다.

## 저장소 구조와 배포 흐름
### 코드와 매니페스트의 분리
애플리케이션 소스 저장소와 배포 매니페스트 저장소를 분리하는 구성이 일반적입니다. 소스가 바뀔 때마다 배포 설정 변경이 섞이면 커밋 이력이 복잡해지고, 배포 승인과 코드 리뷰의 권한 모델도 달라지기 때문입니다.
### 이미지 갱신 흐름
개발자가 소스에 PR을 병합하면 CI가 이미지를 빌드하고 푸시한 뒤 매니페스트 저장소의 이미지 태그를 갱신하는 커밋이나 PR을 만듭니다. 배포 에이전트가 이 변경을 감지해 클러스터에 반영합니다. 환경별로는 `Kustomize` overlay나 `Helm` values로 차이를 관리하고, 운영 환경 변경은 보호 브랜치와 승인자 지정으로 통제합니다.

## 단계적 이행
### 현황 파악과 초기 상태 추출
현재 배포 방식과 리소스를 목록화하고, 실제 클러스터에서 매니페스트를 추출(export)해 Git에 초기 커밋으로 만듭니다. 추출된 매니페스트에는 자동 생성 필드(`status`, `resourceVersion`)가 섞여 있으므로 정리가 필요합니다.
### 시범 적용과 병행 운영
영향이 작은 서비스나 비핵심 환경(개발, 스테이징)부터 GitOps로 전환합니다. 초기에는 자동 동기화를 끄고 수동 동기화로 차이만 확인하다가 신뢰가 쌓이면 자동 동기화를 켭니다. 전환 기간에는 기존 스크립트와 GitOps가 같은 리소스를 건드려 충돌하지 않도록 서비스별 소유권을 명확히 나누고, 이관 완료 시점 이후 수동 변경을 금지합니다.
### 시크릿과 승인 체계
Git에 평문 시크릿을 둘 수 없으므로 `Sealed Secrets`, `SOPS`(암호화 저장), `External Secrets Operator`(외부 저장소 참조) 중 하나를 도입합니다. 운영 환경 변경에는 코드 리뷰어 승인과 보호 브랜치 규칙을 적용해 배포 승인 절차를 Git 워크플로로 일원화합니다.
---
## 운영 고려사항
배포 상태(동기화 여부, 헬스)를 대시보드로 제공하고 동기화 실패 알림을 설정합니다. 롤백은 Git 리버트로 수행하는데, 이때 에이전트가 되돌린 상태를 다시 적용하므로 롤백도 같은 승인 흐름을 따릅니다. 오토스케일러가 바꾸는 레플리카 수 같은 동적 필드는 비교에서 제외해 불필요한 드리프트 경고를 줄입니다. 긴급 상황에서 자동 동기화를 일시 중지하는 절차와, 팀원에게 새 워크플로를 교육하는 계획도 필요합니다.

## 예시 코드
### ArgoCD Application
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: {name: orders, namespace: argocd}
spec:
  source:
    repoURL: https://github.com/org/deploy-manifests
    path: apps/orders/overlays/prod
    targetRevision: main
  destination: {server: https://kubernetes.default.svc, namespace: orders}
  syncPolicy: {automated: {prune: true, selfHeal: true}}
```
### 롤백은 Git 리버트
```bash
git revert <bad-commit> && git push origin main
```

## 전체 요약
- GitOps는 Git의 선언적 상태를 에이전트가 지속적으로 실제 환경에 일치시키는 모델입니다.
- Pull 방식은 클러스터 자격증명 노출을 줄이고 드리프트 감지와 자동 복구를 가능하게 합니다.
- 코드와 매니페스트 저장소를 분리하고 CI가 이미지 태그를 갱신하는 흐름을 만듭니다.
- 클러스터에서 초기 매니페스트를 추출해 Git에 커밋하고 비핵심 서비스부터 점진적으로 이관합니다.
- 전환 기간에는 소유권을 나누어 충돌을 막고 이관 완료 후 수동 변경을 금지합니다.
- 시크릿 암호화 또는 외부 참조, 보호 브랜치 기반 승인으로 안전하게 운영합니다.
