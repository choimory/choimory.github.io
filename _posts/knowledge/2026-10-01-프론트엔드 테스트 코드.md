## 개요

프론트엔드 테스트 코드는 단순히 "화면이 렌더링되는지"만 확인하는 것이 아니라, 사용자의 행동에 따라 UI와 상태가 올바르게 변하는지를 검증하는 코드입니다.

React/Next.js 기준으로는 보통 다음과 같이 나눠서 생각하면 됩니다.

| 종류 | 검증 대상 | 대표 도구 |
| --- | --- | --- |
| Unit Test | 함수, Hook, 유틸 등 작은 단위 | Vitest, Jest |
| Component Test | 컴포넌트 렌더링과 사용자 동작 | React Testing Library |
| Integration Test | 여러 컴포넌트/API/상태의 연동 | React Testing Library + MSW |
| E2E Test | 브라우저에서 실제 사용자 흐름 | Playwright, Cypress |

실무에서는 "Vitest + React Testing Library + MSW + Playwright" 조합이 사용하기 좋습니다.

## Unit Test

Unit Test는 다른 요소와 최대한 분리해서 작은 로직 하나를 검증하는 방식입니다.

예를 들어 가격 계산 함수가 있다고 하면 다음과 같습니다.

```tsx
export function calculateTotal(price: number, quantity: number) {
  return price * quantity;
}
```

테스트는 다음처럼 작성할 수 있습니다.

```tsx
import { describe, expect, it } from 'vitest';
import { calculateTotal } from './calculateTotal';

describe('calculateTotal', () => {
  it('가격과 수량을 곱한 값을 반환한다', () => {
    expect(calculateTotal(1000, 3)).toBe(3000);
  });
});
```

이런 함수는 테스트하기 가장 쉬운 대상입니다.

### 무엇을 Unit Test 하는가

주로 다음과 같은 코드를 테스트합니다.

- formatter
- validator
- 날짜 계산
- 금액 계산
- 데이터 변환 함수
- Custom Hook의 핵심 로직
- 상태 계산 함수

반대로 단순 getter/setter나 너무 단순한 코드까지 전부 테스트할 필요는 없습니다.

## Component Test

프론트엔드에서는 Component Test가 상당히 중요합니다.

예를 들어 다음 버튼이 있다고 가정합니다.

```tsx
interface Props {
  onClick: () => void;
}

export function SubmitButton({ onClick }: Props) {
  return (
    <button onClick={onClick}>
      저장
    </button>
  );
}
```

React Testing Library를 사용하면 다음처럼 테스트할 수 있습니다.

```tsx
import { fireEvent, render, screen } from '@testing-library/react';
import { vi } from 'vitest';

import { SubmitButton } from './SubmitButton';

describe('SubmitButton', () => {
  it('저장 버튼을 클릭하면 onClick이 호출된다', () => {
    const onClick = vi.fn();

    render(
      <SubmitButton onClick={onClick} />
    );

    fireEvent.click(
      screen.getByRole('button', { name: '저장' })
    );

    expect(onClick).toHaveBeenCalledTimes(1);
  });
});
```

하지만 실제로는 `fireEvent`보다 `userEvent`를 사용하는 것이 더 자연스럽습니다.

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { vi } from 'vitest';

it('저장 버튼을 클릭한다', async () => {
  const user = userEvent.setup();
  const onClick = vi.fn();

  render(
    <SubmitButton onClick={onClick} />
  );

  await user.click(
    screen.getByRole('button', { name: '저장' })
  );

  expect(onClick).toHaveBeenCalledOnce();
});
```

`userEvent`는 실제 사용자가 키보드를 입력하거나 버튼을 클릭하는 것과 좀 더 비슷하게 동작합니다.

## React Testing Library의 핵심 개념

React Testing Library에서 중요한 것은 "구현 방식"보다 "사용자가 보는 화면"을 기준으로 테스트하는 것입니다.

예를 들어 아래처럼 접근하는 것을 권장합니다.

```tsx
screen.getByRole('button', {
  name: '회원가입',
});
```

다음과 같이 내부 구현에 강하게 의존하는 테스트는 가능하면 피하는 편이 좋습니다.

```tsx
container.querySelector('.signup-button');
```

컴포넌트의 CSS 클래스가 변경되더라도 실제 사용자 관점에서 기능이 그대로라면 테스트가 깨지지 않는 것이 좋기 때문입니다.

### 권장 우선순위

대체로 다음 순서로 요소를 찾는 것이 좋습니다.

```
getByRole
↓
getByLabelText
↓
getByPlaceholderText
↓
getByText
↓
getByTestId
```

`data-testid`는 마지막 수단 정도로 사용하는 것이 좋습니다.

## API가 포함된 테스트

프론트엔드는 API와 함께 동작하는 경우가 대부분입니다.

예를 들어 다음 컴포넌트가 있다고 가정합니다.

```tsx
export function UserList() {
  const [users, setUsers] = useState<User[]>([]);

  useEffect(() => {
    fetch('/api/users')
      .then(response => response.json())
      .then(setUsers);
  }, []);

  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>
          {user.name}
        </li>
      ))}
    </ul>
  );
}
```

여기서 실제 서버를 호출하면서 테스트하는 것은 좋지 않습니다.

이럴 때 MSW(Mock Service Worker)를 사용할 수 있습니다.

```tsx
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/users', () => {
    return HttpResponse.json([
      {
        id: 1,
        name: '홍길동',
      },
    ]);
  }),
];
```

테스트는 다음처럼 작성합니다.

```tsx
render(<UserList />);

expect(
  await screen.findByText('홍길동')
).toBeInTheDocument();
```

프론트 코드 입장에서는 실제로 HTTP 요청을 보내는 것처럼 동작하지만, 테스트 환경에서는 MSW가 요청을 가로채 응답합니다.

이 방식이 단순히 `fetch`나 `axios` 자체를 Mock 처리하는 것보다 실제 애플리케이션 동작에 가깝습니다.

## 상태별 테스트

컴포넌트를 테스트할 때 성공 케이스만 보는 것은 부족합니다.

API를 사용하는 화면이라면 최소한 다음 상태를 생각하는 것이 좋습니다.

### Loading

```tsx
expect(
  screen.getByText('로딩 중...')
).toBeInTheDocument();
```

### Success

```tsx
expect(
  await screen.findByText('홍길동')
).toBeInTheDocument();
```

### Empty

```tsx
expect(
  screen.getByText('조회된 데이터가 없습니다.')
).toBeInTheDocument();
```

### Error

```tsx
expect(
  await screen.findByText('조회 중 오류가 발생했습니다.')
).toBeInTheDocument();
```

즉 화면 하나에 대해서도 실제 테스트 케이스는 여러 개가 생길 수 있습니다.

## Form 테스트

회원가입 화면을 예로 들면 다음 흐름을 테스트할 수 있습니다.

```
사용자 이름 입력
→ 이메일 입력
→ 저장 버튼 클릭
→ API 요청
→ 성공 메시지 표시
```

예를 들면 다음과 같습니다.

```tsx
const user = userEvent.setup();

render(<SignupForm />);

await user.type(
  screen.getByLabelText('이름'),
  '홍길동'
);

await user.type(
  screen.getByLabelText('이메일'),
  'test@example.com'
);

await user.click(
  screen.getByRole('button', {
    name: '회원가입',
  })
);

expect(
  await screen.findByText('회원가입이 완료되었습니다.')
).toBeInTheDocument();
```

이런 테스트는 실제 사용자가 화면을 사용하는 흐름과 거의 동일합니다.

## E2E Test

E2E 테스트는 가장 큰 범위의 테스트입니다.

예를 들어 다음 전체 흐름을 검사할 수 있습니다.

```
브라우저 실행

→ 로그인 페이지 접속
→ 아이디 입력
→ 비밀번호 입력
→ 로그인
→ 메인페이지 이동
→ 사용자 이름 확인
```

Playwright에서는 다음과 같이 작성할 수 있습니다.

```tsx
import { test, expect } from '@playwright/test';

test('로그인', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('아이디').fill('test');
  await page.getByLabel('비밀번호').fill('password');

  await page
    .getByRole('button', { name: '로그인' })
    .click();

  await expect(page).toHaveURL('/');

  await expect(
    page.getByText('홍길동')
  ).toBeVisible();
});
```

이 단계에서는 React 내부 구조를 신경 쓰지 않습니다.

사용자가 실제 웹사이트를 사용하는 것처럼 브라우저를 조작합니다.

---

## 테스트 범위는 어떻게 나누는가

모든 것을 E2E로 테스트하면 실제 브라우저와 서버가 필요하기 때문에 테스트가 느리고 관리하기 어려워집니다.

반대로 모든 것을 Unit Test로 하면 실제 화면에서 여러 기능이 조합되었을 때 발생하는 문제를 발견하기 어렵습니다.

따라서 보통 다음처럼 나누는 것이 좋습니다.

```
                  E2E
              ──────────
               핵심 흐름

            Integration
        ──────────────────
          화면 + API + 상태

           Component
     ───────────────────────
       사용자 UI Interaction

             Unit
──────────────────────────────
 함수 / Hook / 데이터 변환
```

아래로 갈수록 테스트 개수는 많아지고 빠릅니다.

위로 갈수록 테스트 개수는 적지만 실제 서비스와 비슷한 환경을 검증합니다.

## Next.js 프로젝트라면

현재 Next.js 기반 프론트 프로젝트라면 다음 정도의 구성을 추천할 수 있습니다.

```
Next.js
│
├─ Vitest
│   └─ 테스트 Runner
│
├─ React Testing Library
│   └─ Component / Integration Test
│
├─ MSW
│   └─ API Mock
│
└─ Playwright
    └─ E2E Test
```

Jest도 충분히 사용할 수 있지만 최근 프론트엔드 환경에서는 Vitest를 사용하는 경우도 많습니다.

구조는 예를 들면 다음처럼 만들 수 있습니다.

```
src/
├─ components/
│  └─ Button/
│     ├─ Button.tsx
│     └─ Button.test.tsx
│
├─ features/
│  └─ member/
│     ├─ MemberList.tsx
│     └─ MemberList.test.tsx
│
├─ utils/
│  ├─ formatter.ts
│  └─ formatter.test.ts
│
└─ mocks/
   ├─ handlers.ts
   └─ server.ts

e2e/
├─ login.spec.ts
└─ member.spec.ts
```

개인적으로는 테스트 파일을 별도의 거대한 `tests` 디렉터리에 몰아넣기보다는 테스트 대상 코드 옆에 배치하는 방식이 관리하기 편합니다.

## 무엇까지 테스트해야 하는가

핵심 기준은 "코드가 존재한다는 사실"이 아니라 "사용자 또는 비즈니스 관점에서 깨지면 문제가 되는 동작"입니다.

예를 들어 회원 목록이라면 다음을 테스트하면 됩니다.

```
1. 정상적으로 목록을 조회한다.
2. 로딩 상태가 표시된다.
3. 데이터가 없으면 Empty 화면이 표시된다.
4. API 오류가 발생하면 오류 메시지가 표시된다.
5. 검색어를 입력하면 검색된다.
6. 페이지를 변경하면 새로운 데이터를 조회한다.
7. 사용자를 클릭하면 상세 화면으로 이동한다.
```

반면 다음처럼 테스트하는 것은 가치가 낮을 수 있습니다.

```
useState가 호출되었는가?
useEffect가 호출되었는가?
내부 함수 이름이 xxx인가?
특정 div가 정확히 3개인가?
```

내부 구현보다는 "결과"를 테스트하는 것이 중요합니다.

## 전체 요약

프론트엔드 테스트는 다음 구조로 생각하면 가장 이해하기 쉽습니다.

```
Unit
→ 순수 함수 / Hook / 계산 로직

Component
→ 컴포넌트 렌더링 / 클릭 / 입력

Integration
→ 화면 + 상태 + API 연동

E2E
→ 실제 브라우저에서 전체 사용자 흐름
```

Next.js/React라면 실무 구성은 다음 조합이 무난합니다.

```
Vitest
+
React Testing Library
+
MSW
+
Playwright
```

그리고 가장 중요한 원칙은 다음입니다.

"컴포넌트 내부 구현이 아니라 실제 사용자가 경험하는 동작을 테스트한다."
