## 개요

VPN(Virtual Private Network)은 "공용 네트워크인 인터넷을 통해 사설 네트워크에 안전하게 접근할 수 있도록 논리적인 전용 통신 경로를 구성하는 기술"입니다.

VPN의 핵심은 "터널링(Tunneling)"과 "암호화(Encryption)"입니다. 인터넷 위에 가상의 사설 통신 경로를 만들어 외부에서도 내부 네트워크에 안전하게 접근할 수 있습니다.

대표적인 사용 상황은 재택근무자의 사내망 접속, 외부 개발자의 SSH 접속, 데이터센터 간 통신, 온프레미스와 AWS VPC 연결, 공용 Wi-Fi에서 VPN 서버까지의 통신 보호 등입니다.

VPN은 단순히 IP 주소를 변경하는 기술이 아니라 "네트워크 간 또는 사용자와 네트워크 간에 안전한 통신 경로를 제공하는 기술"입니다.

---

## 1. VPN이 필요한 이유

### 1.1 공용 네트워크와 사설 네트워크

일반적으로 기업 내부 네트워크는 외부 인터넷과 분리되어 있습니다.

```
회사 내부 네트워크
192.168.10.0/24

├── 개발 서버: 192.168.10.10
├── DB 서버: 192.168.10.20
└── 모니터링 서버: 192.168.10.30
```

`192.168.x.x`는 사설 IP이며 인터넷에서 직접 라우팅되지 않으므로 외부에서 내부 서버에 직접 접근할 수 없습니다.

### 1.2 외부에서 내부 서버에 접근하려면?

```
집의 개발자 → 인터넷 → 회사 네트워크 → 개발 서버(192.168.10.10)
```

외부 인터넷에는 회사 내부 사설 네트워크로 향하는 경로가 일반적으로 존재하지 않습니다.

이를 해결하는 방법에는 공인 IP 할당, 포트 포워딩, Bastion Host, VPN 등이 있습니다. VPN은 내부 서버를 직접 노출하지 않고 사설 네트워크에 접근하도록 구성할 수 있는 방법입니다.

## 2. VPN의 동작 원리

VPN은 터널링, 암호화, 인증을 기반으로 동작합니다.

### 2.1 터널링(Tunneling)

터널링은 "하나의 네트워크 패킷을 다른 네트워크 패킷 안에 캡슐화하여 전달하는 기술"입니다.

```
VPN 클라이언트 ── 인터넷 / 암호화된 VPN 터널 ── VPN 서버
                                                   │
                                                   ▼
                                         내부 개발 서버
                                         192.168.10.10
```

```
원본 IP 패킷
┌──────────────────────────┐
│ 목적지: 192.168.10.10    │
│ 데이터: SSH 요청         │
└──────────────────────────┘
            ↓ 캡슐화 및 암호화
외부 전송 패킷
┌──────────────────────────┐
│ 출발지: 개발자 공인 IP   │
│ 목적지: VPN 서버 공인 IP │
│ 암호화된 원본 IP 패킷    │
└──────────────────────────┘
```

VPN 서버는 수신한 패킷을 복호화하고 캡슐화 해제(Decapsulation)한 뒤 내부 네트워크로 전달합니다.

### 2.2 암호화(Encryption)

터널링 자체가 반드시 암호화를 의미하지는 않습니다. VPN 프로토콜은 보통 암호화와 무결성 보호 기능을 제공합니다.

VPN 클라이언트와 VPN 서버 사이의 통신을 보호하더라도 VPN 서버에서 최종 목적지까지의 구간이 자동으로 종단 간 암호화되는 것은 아닙니다.

### 2.3 인증(Authentication)

VPN 서버는 접속자를 확인합니다. ID/Password, 인증서, 공개키, MFA, SSO 등의 인증 방식이 있습니다.

VPN 인증 이후에도 방화벽, ACL, 사용자 권한을 통해 접근 가능한 네트워크와 서버를 제한해야 합니다.

## 3. VPN의 종류

### 3.1 Remote Access VPN

Remote Access VPN은 "개별 사용자 또는 장치가 외부에서 사설 네트워크에 접속하기 위한 VPN"입니다.

```
개발자 노트북 → 인터넷 → VPN 서버 → 회사 내부 네트워크
                                      ├── 개발 서버
                                      ├── DB 서버
                                      └── Kubernetes Cluster
```

재택근무, 사내 서버 접근, Kubernetes API 접근, 원격 서버 관리에 활용합니다.

```bash
ssh ubuntu@192.168.10.10
```

VPN 연결만으로 접근이 보장되는 것은 아니며 라우팅 경로와 방화벽 정책도 올바르게 구성되어야 합니다.

### 3.2 Site-to-Site VPN

Site-to-Site VPN은 "서로 다른 두 네트워크를 VPN 터널을 통해 연결하는 방식"입니다. 사용자가 아니라 VPN 게이트웨이끼리 연결됩니다.

```
서울 본사 (192.168.10.0/24)
       │
VPN Gateway A
       │ 암호화된 VPN 터널
VPN Gateway B
       │
부산 지사 (192.168.20.0/24)
```

본사와 지사, 데이터센터, 온프레미스와 클라우드, 서로 다른 클라우드 네트워크 연결에 사용합니다.

### 3.3 VPN 유형 비교

| 구분 | Remote Access VPN | Site-to-Site VPN |
| --- | --- | --- |
| 연결 단위 | 사용자 또는 장치 | 네트워크 간 |
| 주요 목적 | 외부에서 내부 접근 | 서로 다른 네트워크 연결 |
| 연결 주체 | VPN Client | VPN Gateway |
| 대표 사례 | 재택근무, 원격 관리 | 본사-지사, 온프레미스-AWS |
| 대표 기술 | WireGuard, OpenVPN | IPsec VPN |

## 4. VPN에서 IP 주소는 어떻게 동작할까?

VPN에 연결하면 가상 네트워크 인터페이스가 생성되거나 활성화됩니다.

```
개발자 노트북
Wi-Fi 인터페이스: 192.168.0.100
VPN 인터페이스: 10.8.0.2

VPN 서버
공인 IP: 203.0.113.10
VPN 인터페이스: 10.8.0.1
내부 네트워크: 192.168.10.0/24
```

203.0.113.10은 설명을 위한 문서용 예시 IP입니다.

```
개발자 노트북(10.8.0.2)
       │ 목적지: 192.168.10.10
       ▼
VPN 터널 → VPN 서버(10.8.0.1)
                    │ 내부망 라우팅
                    ▼
             개발 서버(192.168.10.10)
```

VPN을 연결한다고 해서 모든 트래픽이 자동으로 VPN을 통과하는 것은 아닙니다. 트래픽이 어느 인터페이스를 통과하는지는 라우팅 테이블에 따라 결정됩니다.

## 5. Full Tunnel과 Split Tunnel

### 5.1 Full Tunnel

Full Tunnel은 "인터넷을 포함한 일반적인 외부 트래픽을 VPN 서버를 통해 전달하는 방식"입니다.

```
개발자 노트북 → VPN 서버 ┬→ 회사 내부 서버
                        └→ 일반 인터넷 (google.com)
```

일반적으로 기본 경로(Default Route)가 VPN 인터페이스를 사용하도록 변경됩니다.

장점은 중앙 보안 정책으로 트래픽을 통제하기 쉽다는 점입니다. 반면 VPN 서버의 대역폭과 처리 성능이 중요해집니다. VPN 서버 자체에 도달하기 위한 경로 등을 별도로 유지할 수 있습니다.

### 5.2 Split Tunnel

Split Tunnel은 "특정 네트워크로 향하는 트래픽만 VPN을 통해 전달하는 방식"입니다.

```
개발자 노트북 ┬→ 192.168.10.0/24 → VPN → 회사 내부
              └→ 일반 인터넷 → google.com
```

```
Destination        Gateway / Interface
192.168.10.0/24    VPN Interface
0.0.0.0/0          Wi-Fi Gateway
```

내부 서버에 접근하는 트래픽만 VPN으로 전달되고 일반 인터넷 트래픽은 기존 회선을 사용합니다.

### 5.3 Full Tunnel과 Split Tunnel 비교

| 구분 | Full Tunnel | Split Tunnel |
| --- | --- | --- |
| VPN 사용 범위 | 대부분의 트래픽 | 지정된 네트워크 |
| 일반 인터넷 | VPN 경유 | 직접 접속 |
| VPN 서버 부하 | 상대적으로 높음 | 상대적으로 낮음 |
| 중앙 보안 통제 | 상대적으로 용이 | 별도 정책 관리 필요 |
| 주요 활용 | 기업 보안 중심 환경 | 개발 및 원격 접속 환경 |

개발자가 내부 Kubernetes Cluster나 개발 서버에 접근하려는 목적이라면 Split Tunnel이 유용할 수 있습니다.

## 6. 대표적인 VPN 기술

### 6.1 IPsec

IPsec(Internet Protocol Security)은 IP 계층에서 통신을 보호하기 위한 프로토콜 집합입니다.

- IP 계층에서 데이터 보호
- 암호화 및 무결성 검증
- IKE를 통한 보안 연결 협상
- 기업 네트워크 및 클라우드 VPN에서 활용

AWS Site-to-Site VPN에서도 IPsec을 사용합니다.

### 6.2 OpenVPN

OpenVPN은 TLS를 기반으로 보안 터널을 구성하는 VPN 기술입니다.

- UDP 또는 TCP 기반 통신 지원
- 인증서 기반 인증 지원
- 다양한 운영체제 지원
- 세밀한 서버 및 클라이언트 설정 가능

전통적인 원격 접속 VPN 구축에 많이 사용됩니다.

### 6.3 WireGuard

WireGuard는 간결한 구조와 현대적인 암호화 기술을 특징으로 하는 VPN입니다.

- UDP 기반 통신
- 공개키 기반 피어 인증
- 비교적 간단한 설정
- 작은 코드베이스
- 효율적인 네트워크 처리

Linux 서버와 개발 환경에서 VPN을 직접 구축할 때 유용합니다.

### 6.4 Tailscale

Tailscale은 WireGuard를 활용하여 장치 간 VPN 연결을 쉽게 구성하도록 도와주는 서비스입니다.

일반적인 VPN은 VPN 서버, 인증, 라우팅, NAT 등을 직접 구성해야 할 수 있습니다. Tailscale은 장치 인증, 피어 검색, NAT 통과, 접근 정책 등을 관리하여 부담을 줄입니다.

가능하면 장치 간 직접 연결을 사용하고 직접 연결이 어려운 경우 릴레이를 활용합니다.

| 구분 | IPsec | OpenVPN | WireGuard | Tailscale |
| --- | --- | --- | --- | --- |
| 성격 | 보안 프로토콜 집합 | VPN 프로토콜 및 소프트웨어 | VPN 프로토콜 및 소프트웨어 | VPN 네트워크 서비스 |
| 활용 | 기업망 및 클라우드 | 원격 접속 | 원격 접속 및 서버 연결 | 장치 간 사설 네트워크 |
| 설정 난이도 | 비교적 높음 | 중간~높음 | 비교적 낮음 | 비교적 낮음 |
| 주요 특징 | 폭넓은 기업 장비 지원 | 유연한 설정 | 경량화 및 효율성 | 관리 편의성 |

## 7. VPN과 DevOps 인프라

### 7.1 Kubernetes Cluster 접근

Kubernetes Control Plane의 API Server는 클러스터를 관리하는 진입점입니다.

```
개발자 노트북
      │
      ▼
VPN → 내부 네트워크
            │
            ▼
Kubernetes API Server
192.168.10.100:6443
            │
            ▼
Kubernetes Cluster
```

외부 개발자가 API Server에 직접 접근할 수 없도록 구성하고 VPN을 통해 접근하게 할 수 있습니다.

```bash
kubectl get nodes
kubectl get pods -A
```

VPN은 네트워크 접근 경로를 제공할 뿐입니다. Kubernetes API Server의 사용자 인증과 권한 관리는 RBAC 등으로 별도로 수행해야 합니다.

### 7.2 내부 관리 시스템 접근

운영 환경에서는 Grafana, Prometheus, Argo CD, Jenkins, 내부 Git 서버, 데이터베이스 관리 인터페이스 등을 외부 인터넷에 직접 공개하지 않는 경우가 많습니다.

```
외부 개발자 → VPN → Private Network
                       ├── Argo CD
                       ├── Grafana
                       ├── Jenkins
                       └── Kubernetes API
```

이 구조는 불필요한 외부 공격 표면을 줄이는 데 도움이 됩니다. 하지만 VPN 접속과 별개로 서비스별 인증과 네트워크 접근 제어도 적용해야 합니다.

### 7.3 온프레미스와 AWS 연결

```
온프레미스 (192.168.10.0/24)
        │
        ▼
VPN Gateway
        │ IPsec VPN
        ▼
AWS Site-to-Site VPN
        │
        ▼
AWS VPC (10.0.0.0/16)
        ├── EC2
        ├── RDS
        └── EKS
```

온프레미스 서버와 AWS VPC 내부 리소스가 사설 주소로 통신할 수 있습니다.

필요한 설정에는 VPN 게이트웨이와 터널, 라우팅 테이블, Security Group, Network ACL 및 방화벽, CIDR 중복 여부 확인 등이 있습니다.

AWS Site-to-Site VPN의 트래픽은 인터넷 등을 통해 전송될 수 있지만 VPN 터널을 통해 암호화됩니다.

## 8. Linux에서 VPN 확인하기

### 8.1 네트워크 인터페이스 확인

```bash
ip addr
```

WireGuard에서는 다음과 같은 인터페이스가 나타날 수 있습니다.

```
wg0:
    inet 10.8.0.2/24
```

`wg0`는 VPN 통신에 사용하는 가상 네트워크 인터페이스입니다.

### 8.2 라우팅 테이블 확인

```bash
ip route
```

```
default via 192.168.0.1 dev wlan0
192.168.10.0/24 dev wg0
192.168.0.0/24 dev wlan0
```

`192.168.10.0/24` 네트워크 트래픽만 `wg0`를 통과하므로 Split Tunnel 구성입니다.

### 8.3 특정 목적지에 대한 경로 확인

```bash
ip route get 192.168.10.10
```

특정 목적지에 선택되는 경로를 확인할 수 있습니다. 정책 라우팅을 사용하는 VPN에서는 `ip rule` 및 별도 라우팅 테이블도 확인해야 합니다.

## 9. VPN 사용 시 주의할 점

### 인증과 권한 분리

VPN은 네트워크 접근 수단일 뿐입니다. VPN 접속 이후에도 별도의 인증 및 권한 체계가 필요합니다. 개발자와 운영자의 서버 접근 권한 등을 분리하는 것이 좋습니다.

### 네트워크 대역 충돌

집 네트워크와 회사 네트워크가 모두 `192.168.0.0/24`를 사용하는 등 동일한 CIDR이 겹치면 라우팅 충돌이 발생할 수 있습니다. VPN 설계에서는 사설 네트워크 대역 중복을 방지해야 합니다.

### VPN 서버의 보안

VPN 서버는 외부에서 내부 네트워크로 접근하는 진입점이 될 수 있습니다.

- VPN 소프트웨어 최신 보안 업데이트
- MFA 및 인증서 관리
- 최소 권한 접근 정책
- 접속 로그 및 모니터링
- 불필요한 내부 네트워크 접근 차단

## 전체 요약

VPN은 "인터넷과 같은 공용 네트워크 위에 논리적인 사설 통신 경로를 구성하여 안전한 네트워크 접근을 제공하는 기술"입니다.

| 핵심 개념 | 설명 |
| --- | --- |
| VPN | 가상의 사설 통신 경로 구성 |
| Tunneling | 패킷을 캡슐화하여 전달 |
| Encryption | 통신 내용 보호 |
| Authentication | 접속 사용자 또는 장치 인증 |
| Remote Access VPN | 외부 사용자와 내부 네트워크 연결 |
| Site-to-Site VPN | 서로 다른 네트워크 간 연결 |
| Full Tunnel | 대부분의 트래픽을 VPN 경유 |
| Split Tunnel | 지정된 네트워크 트래픽만 VPN 경유 |
| VPN Interface | VPN 통신에 사용하는 가상 인터페이스 |
| VPN Gateway | VPN 패킷을 처리하고 네트워크 간 전달 |

DevOps 관점에서 VPN의 중요한 역할은 "외부에 공개하지 않은 Private Network의 인프라에 안전하게 접근할 수 있는 통신 경로를 제공하는 것"입니다.

특히 Kubernetes API Server, Argo CD, Grafana, Jenkins 등의 내부 관리 시스템과 온프레미스·클라우드 네트워크를 연결할 때 유용합니다.
