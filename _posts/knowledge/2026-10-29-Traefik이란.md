## 개요

"Traefik(트래픽)"은 클라우드 네이티브 환경에 최적화된 오픈소스 "리버스 프록시(Reverse Proxy)이자 로드 밸런서(Load Balancer), Ingress Controller"입니다.

Docker, Kubernetes와 같은 컨테이너 환경에서 외부 요청을 적절한 서비스로 전달하고, 서비스의 생성·삭제·변경을 자동으로 감지하여 라우팅 설정을 동적으로 관리하는 것이 가장 큰 특징입니다.

기존 Nginx와 유사한 역할을 수행하지만, Traefik은 컨테이너 기반의 동적 인프라를 고려하여 설계되었다는 차이점이 있습니다.

핵심 기능은 다음과 같습니다.

- "Reverse Proxy": 클라이언트 요청을 내부 서비스에 전달합니다.
- "Load Balancing": 여러 서버 또는 컨테이너에 트래픽을 분산합니다.
- "Service Discovery": Docker, Kubernetes의 서비스 정보를 자동으로 탐색합니다.
- "Dynamic Configuration": 서비스 변경을 감지하고 라우팅 설정을 동적으로 갱신합니다.
- "TLS/HTTPS": HTTPS 통신과 인증서를 관리합니다.
- "Middleware": 인증, 리다이렉션, Rate Limit 등의 기능을 제공합니다.
- "Ingress Controller": Kubernetes 외부 트래픽을 클러스터 내부 서비스로 전달합니다.

## 1. Traefik이 등장한 배경

### 1.1 기존 Reverse Proxy의 한계

전통적인 서버 환경에서는 Nginx나 HAProxy를 이용하여 여러 애플리케이션으로 트래픽을 분산했습니다.

예를 들어 다음과 같은 구조입니다.

```
Client
   |
   v
Nginx (Reverse Proxy)
   |
   +----> App Server 1
   +----> App Server 2
   +----> App Server 3
```

Nginx에서 트래픽을 전달하려면 일반적으로 설정 파일에 대상 서버를 정의합니다.

```
upstream backend {
    server 10.0.0.10:8080;
    server 10.0.0.11:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

이러한 정적 설정 방식에서는 서버가 추가되거나 삭제될 때 대상 서버 목록을 수정하고 설정을 다시 적용해야 할 수 있습니다.

물론 Nginx 역시 동적 설정과 서비스 디스커버리를 지원할 수 있지만, 이를 위한 별도의 구성이나 연동이 필요한 경우가 있습니다.

### 1.2 컨테이너 환경에서 발생하는 문제

Docker나 Kubernetes에서는 다음과 같은 상황이 빈번하게 발생합니다.

- 컨테이너가 생성되거나 삭제됩니다.
- Pod가 재시작되면서 IP 주소가 변경됩니다.
- 오토스케일링으로 애플리케이션 인스턴스가 증가하거나 감소합니다.
- 새로운 서비스가 배포됩니다.
- 서비스별 라우팅 규칙이 변경됩니다.

이러한 상황에서 매번 프록시 설정을 수동으로 수정하는 방식은 비효율적입니다.

Traefik은 이 문제를 해결하기 위해 "인프라의 상태를 감지하고 라우팅 구성을 자동으로 갱신"하는 방식으로 동작합니다.

## 2. Traefik의 주요 아키텍처

Traefik은 크게 다섯 가지 구성요소를 중심으로 동작합니다.

```
Client Request
https://api.example.com
       |
       v
EntryPoint (HTTP :80 / HTTPS :443)
       |
       v
Router (Host / Path 기반 라우팅)
       |
       v
Middleware (인증 / Rate Limit / Redirect)
       |
       v
Traefik Service (Load Balancing)
       |
       +----> Pod 1
       +----> Pod 2
       +----> Pod 3

Provider (Docker / Kubernetes / File)
  └─ 인프라 상태를 감지하여 라우팅 설정을 동적으로 제공
```

개념도입니다. Middleware는 Router에 연결되며, 필요하지 않은 경우 생략할 수 있습니다. Provider는 요청 경로가 아니라 설정을 공급하는 구성요소입니다.

### 2.1 EntryPoint

EntryPoint는 Traefik이 외부 요청을 수신하는 네트워크 진입점입니다.

일반적으로 HTTP와 HTTPS 포트를 설정합니다.

| EntryPoint | 포트 | 프로토콜 |
| --- | --- | --- |
| web | 80 | HTTP |
| websecure | 443 | HTTPS |

즉, 클라이언트가 Traefik으로 요청을 보낼 때 가장 먼저 도달하는 지점입니다.

### 2.2 Router

Router는 클라이언트 요청을 분석하여 어떤 서비스로 전달할지 결정합니다.

주로 다음 조건을 사용합니다.

- Host: 도메인 기반 라우팅
- Path: 경로 기반 라우팅
- PathPrefix: 경로 접두사 기반 라우팅
- Header: HTTP 헤더 기반 라우팅

예를 들어 다음과 같이 구성할 수 있습니다.

| 요청 URL | 전달 대상 |
| --- | --- |
| api.example.com | API Server |
| admin.example.com | Admin Server |
| example.com | Frontend Server |

### 2.3 Middleware

Middleware는 요청이 실제 서비스에 전달되기 전이나 응답을 반환하는 과정에서 추가적인 처리를 수행하는 기능입니다.

대표적인 기능은 다음과 같습니다.

| 기능 | 설명 |
| --- | --- |
| BasicAuth | HTTP 기본 인증 |
| RateLimit | 요청 횟수 제한 |
| RedirectScheme | HTTP → HTTPS 리다이렉션 |
| StripPrefix | URL 경로 접두사 제거 |
| Headers | HTTP 헤더 추가 및 수정 |
| Compress | 응답 압축 |
| Retry | 실패 요청 재시도 |

여러 Middleware를 하나의 Router에 연결할 수도 있습니다.

### 2.4 Service

Traefik에서 Service는 실제 요청을 전달할 백엔드 대상을 나타내는 라우팅 구성요소입니다.

여러 서버를 대상으로 Load Balancing을 수행할 수 있습니다.

여기서 주의할 점은 "Traefik Service"와 "Kubernetes Service"는 서로 다른 개념이라는 것입니다.

Traefik Service는 프록시 내부의 논리적인 백엔드 구성이고, Kubernetes Service는 Pod에 대한 안정적인 네트워크 접근을 제공하는 Kubernetes 리소스입니다.

### 2.5 Provider

Provider는 Traefik이 라우팅 설정을 어디에서 가져올지 결정하는 구성요소입니다.

| Provider | 설명 |
| --- | --- |
| Docker | Docker 컨테이너와 Label 감지 |
| Kubernetes Ingress | Kubernetes Ingress 리소스 감지 |
| Kubernetes CRD | IngressRoute 등 Traefik 전용 리소스 감지 |
| Kubernetes Gateway | Gateway API 리소스 감지 |
| File | YAML 또는 TOML 파일 기반 설정 |

예를 들어 Docker Provider를 활성화하면 Docker 이벤트와 컨테이너 Label을 기반으로 라우팅을 구성할 수 있습니다.

Kubernetes에서는 Kubernetes API를 통해 리소스 변경을 감지하고 라우팅 설정을 갱신합니다.

## 3. Kubernetes에서의 Traefik

Kubernetes 환경에서 Traefik은 주로 "Ingress Controller" 또는 "Gateway API Controller" 역할을 수행합니다.

### 3.1 Kubernetes Ingress Controller

Kubernetes의 Ingress는 외부 HTTP/HTTPS 요청을 내부 Service로 전달하기 위한 라우팅 규칙을 정의하는 API 리소스입니다.

하지만 Ingress 리소스 자체는 실제 트래픽을 전달하지 않습니다.

Ingress 규칙을 해석하고 적용할 "Ingress Controller"가 필요합니다.

Traefik이 바로 이 역할을 수행할 수 있습니다.

```
Internet
   |
   v
LoadBalancer
   |
   v
Traefik Ingress Controller
   |
   v
Ingress
   |
   v
Kubernetes Service
   |
   v
Pod
```

이 구조에서 Ingress는 실제 네트워크 홉이라기보다 Traefik이 참조하는 라우팅 규칙입니다.

Traefik은 Ingress 리소스를 감지하여 요청을 적절한 Kubernetes Service로 전달합니다.

### 3.2 Traefik IngressRoute

Traefik은 Kubernetes 표준 Ingress 외에도 자체 CRD인 "IngressRoute"를 제공합니다.

IngressRoute를 사용하면 Traefik의 라우팅 기능을 Kubernetes 리소스로 선언적으로 관리할 수 있습니다.

| 항목 | Ingress | IngressRoute |
| --- | --- | --- |
| 정의 주체 | Kubernetes | Traefik |
| 리소스 유형 | 표준 API | Traefik CRD |
| 기본 HTTP 라우팅 | 지원 | 지원 |
| Traefik Middleware 연동 | Annotation 등으로 연동 | 리소스 직접 참조 |
| Traefik 전용 기능 | 확장 방식으로 사용 | 직접 설정 가능 |
| 이식성 | 상대적으로 높음 | Traefik 종속 |

IngressRoute는 Traefik 전용 기능을 적극적으로 활용하는 환경에 적합합니다.

반대로 특정 Ingress Controller에 대한 종속성을 줄이고 싶다면 표준 Ingress나 Gateway API를 고려할 수 있습니다.

### 3.3 Gateway API와 Traefik

Traefik은 Kubernetes Gateway API도 지원합니다.

Gateway API는 기존 Ingress의 한계를 보완하기 위해 개발된 Kubernetes 네트워크 API입니다.

주요 리소스는 다음과 같습니다.

- GatewayClass: Gateway를 구현할 Controller를 지정합니다.
- Gateway: 트래픽 수신 지점을 정의합니다.
- HTTPRoute: HTTP 요청 라우팅 규칙을 정의합니다.
- GRPCRoute: gRPC 요청 라우팅 규칙을 정의합니다.

Traefik은 Gateway API 리소스를 해석하는 Controller로 사용할 수 있습니다.

현재 Kubernetes Ingress API는 기능이 동결된 상태이며, Traefik 공식 문서에서도 새로운 구성에는 Gateway API 사용을 권장합니다.

## 4. Traefik과 Nginx의 차이점

Traefik과 Nginx는 모두 Reverse Proxy와 Load Balancing 기능을 제공하지만, 설계 방향과 운영 경험에 차이가 있습니다.

| 비교 항목 | Traefik | Nginx OSS |
| --- | --- | --- |
| 주요 설계 방향 | 클라우드 네이티브 프록시 | 범용 웹 서버 및 프록시 |
| Reverse Proxy | 지원 | 지원 |
| Load Balancing | 지원 | 지원 |
| Docker 자동 탐색 | 기본 Provider 지원 | 일반적으로 별도 연동 필요 |
| Kubernetes 연동 | 기본 Provider 지원 | 별도 Controller 구성 |
| 설정 방식 | Provider, CRD, Label 등 | 설정 파일 중심 |
| 동적 설정 | 핵심 기능 | 구성 방식에 따라 지원 |
| Let's Encrypt | ACME 자동화 내장 | 일반적으로 별도 도구 사용 |
| Web Server 기능 | 주목적 아님 | 정적 파일 제공 등 지원 |
| Middleware | 내장 라우팅 기능 | 모듈 및 설정 활용 |

### 4.1 Traefik이 유리한 상황

- Docker Compose 기반으로 여러 서비스를 운영하는 경우
- Kubernetes 환경에서 Ingress Controller가 필요한 경우
- 서비스가 자주 생성되거나 삭제되는 경우
- HTTPS 인증서 관리를 자동화하고 싶은 경우
- GitOps 기반으로 라우팅을 선언적으로 관리하려는 경우

### 4.2 Nginx가 유리한 상황

- 정적 파일을 직접 제공하는 웹 서버가 필요한 경우
- 기존 Nginx 설정 및 운영 노하우를 활용하는 경우
- 세밀한 HTTP 처리와 프록시 튜닝이 필요한 경우
- 컨테이너보다는 고정적인 서버 환경을 운영하는 경우

두 솔루션은 반드시 서로 대체해야 하는 관계는 아닙니다.

예를 들어 Traefik이 외부 트래픽을 수신하고, 내부의 Nginx가 정적 웹 애플리케이션을 제공하는 구조도 가능합니다.

## 5. Traefik과 다른 Kubernetes 네트워크 구성요소 비교

Traefik의 역할을 이해하려면 LoadBalancer, Ingress, Gateway API와의 관계를 구분해야 합니다.

| 구성요소 | 주요 역할 |
| --- | --- |
| LoadBalancer | 외부에서 내부 네트워크로 트래픽을 전달할 진입점 제공 |
| Ingress | HTTP/HTTPS 라우팅 규칙 정의 |
| Ingress Controller | Ingress 규칙을 실제 프록시에 반영 |
| Gateway API | Gateway 및 트래픽 라우팅을 선언적으로 정의 |
| Traefik | Ingress/Gateway API를 구현하고 실제 트래픽을 처리 |
| Nginx | 웹 서버 또는 Reverse Proxy로 사용 |

여기서 중요한 사실은 "Traefik이 LoadBalancer Service 자체를 대체하는 것은 아니다"라는 점입니다.

일반적인 Kubernetes 구성에서는 다음과 같이 결합하여 사용합니다.

```
Internet
   |
   v
Cloud Load Balancer
   |
   v
Kubernetes Service (LoadBalancer)
   |
   v
Traefik Pod
   |
   v
Application Service
   |
   v
Application Pod
```

클라우드 환경에서는 LoadBalancer 타입 Service를 통해 외부 Load Balancer를 프로비저닝하고, Traefik이 그 뒤에서 L7 라우팅을 담당하는 구성이 일반적입니다.

반면 온프레미스 Kubernetes에서는 MetalLB 등의 솔루션이나 별도의 외부 로드 밸런서를 함께 구성할 수 있습니다.

즉, Traefik은 "외부 트래픽의 HTTP 라우팅을 관리하는 역할"에 가깝습니다.

## 6. Traefik 활용 예시

### 6.1 Docker Compose에서 사용

Docker에서는 컨테이너 Label을 이용하여 라우팅 규칙을 정의할 수 있습니다.

다음은 Traefik이 HTTP 요청을 Nginx 컨테이너에 전달하는 간단한 예시입니다.

```yaml
services:
  traefik:
    image: traefik:v3.7
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false
      - --entrypoints.web.address=:80
    ports:
      - "80:80"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro

  web:
    image: nginx:alpine
    labels:
      - traefik.enable=true
      - traefik.http.routers.web.rule=Host(`web.example.com`)
      - traefik.http.routers.web.entrypoints=web
      - traefik.http.services.web.loadbalancer.server.port=80
```

위 구성에서는 다음과 같이 동작합니다.

1. Traefik이 Docker Provider를 통해 컨테이너 정보를 조회합니다.
2. Nginx 컨테이너에 설정된 Label을 확인합니다.
3. `web.example.com`으로 들어온 요청을 Nginx 컨테이너로 전달합니다.
4. 컨테이너의 상태가 변경되면 Traefik이 라우팅 정보를 동적으로 갱신합니다.

실제 운영 환경에서는 Docker Socket 접근 권한을 최소화하고, Socket Proxy 등의 격리 방식을 고려하는 것이 좋습니다.

### 6.2 Kubernetes에서 사용

Kubernetes에서는 일반 Ingress를 사용하여 Traefik에 라우팅 규칙을 전달할 수 있습니다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  ingressClassName: traefik
  rules:
    - host: web.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
```

이 설정은 다음을 의미합니다.

- `web.example.com`으로 들어온 요청을 처리합니다.
- `traefik` IngressClass를 사용하는 Controller가 처리합니다.
- 요청을 `web-service:80`으로 전달합니다.

단, Traefik Controller와 해당 IngressClass가 미리 설치 및 설정되어 있어야 합니다.

이 예시에서는 TLS와 인증서 설정을 생략했습니다.

## 7. DevOps 환경에서 Traefik을 사용하는 이유

Traefik은 특히 Kubernetes, Docker Compose, Helm, Argo CD와 같은 도구를 활용하는 환경에서 유용합니다.

### 7.1 GitOps와의 연계

Traefik은 Ingress, IngressRoute, Gateway API 같은 Kubernetes 리소스를 통해 라우팅 규칙을 관리할 수 있습니다.

따라서 Git 저장소에 라우팅 설정을 선언하고 Argo CD로 배포하는 GitOps 운영 방식과 잘 어울립니다.

예를 들어 다음과 같은 구조를 구성할 수 있습니다.

```
Git Repository
      |
      v
Argo CD
      |
      +----> Traefik
      |
      +----> Ingress / HTTPRoute
      |
      +----> Application
```

Argo CD는 Git에 정의된 리소스를 Kubernetes에 배포하고, Traefik은 생성된 라우팅 리소스를 감지하여 실제 네트워크 구성을 반영합니다.

따라서 "Argo CD는 선언된 상태를 배포하고, Traefik은 선언된 네트워크 정책을 실행한다"라고 이해하면 됩니다.

### 7.2 자체 구축 Kubernetes에서 활용

클라우드의 Managed Kubernetes가 아닌, 직접 설치한 Kubernetes 환경에서도 Traefik을 사용할 수 있습니다.

예를 들어 다음과 같습니다.

```
External Client
      |
      v
Router / Firewall
      |
      v
MetalLB VIP
      |
      v
Traefik
      |
      v
Kubernetes Service
      |
      v
Pod
```

MetalLB가 외부 접근용 IP를 제공하고 Traefik이 HTTP/HTTPS 요청을 내부 서비스로 라우팅하는 방식입니다.

이 조합을 사용하면 클라우드에서 제공하는 관리형 로드 밸런서에 의존하지 않고도 Kubernetes 외부 트래픽을 처리할 수 있습니다.

단, MetalLB는 주로 베어메탈 환경에서 LoadBalancer 타입 Service에 IP를 할당하고 연결성을 제공하는 역할이며, 외부 네트워크에서 해당 IP까지 실제로 접근할 수 있도록 라우팅을 구성해야 합니다.

## 전체 요약

Traefik은 "Docker와 Kubernetes 같은 동적 인프라에서 서비스 탐색, 라우팅, 로드 밸런싱을 자동화하는 Reverse Proxy"입니다.

| 구분 | 핵심 내용 |
| --- | --- |
| 정체 | Reverse Proxy, Load Balancer, Ingress Controller |
| 주요 목적 | 외부 트래픽을 적절한 내부 서비스로 전달 |
| 핵심 특징 | Service Discovery와 동적 설정 |
| 주요 구성요소 | EntryPoint, Router, Middleware, Service, Provider |
| Docker 연동 | Docker Label을 기반으로 라우팅 구성 |
| Kubernetes 연동 | Ingress, IngressRoute, Gateway API 지원 |
| Nginx와의 차이 | 컨테이너 환경의 자동 탐색 및 동적 구성에 중점 |
| GitOps 연동 | Helm, Argo CD와 결합하여 선언적으로 관리 가능 |

결론적으로 Traefik은 단순히 Nginx를 대체하는 프록시가 아니라, "컨테이너 및 Kubernetes 환경에서 서비스 변경에 따라 네트워크 라우팅을 자동으로 관리할 수 있는 클라우드 네이티브 프록시"라고 이해하는 것이 가장 적절합니다.
