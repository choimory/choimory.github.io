## 개요

로그와 모니터링은 장애가 났을 때 "무슨 일이 벌어졌는가"를 알려 주는 시스템의 눈입니다. 설계가 부실하면 장애를 사용자 제보로 알게 되고, 원인을 찾느라 몇 시간을 쓰며, 반대로 로그가 너무 많거나 알림이 과하면 정작 중요한 신호가 묻힙니다. 좋은 설계는 필요한 것을 필요한 수준으로 남기고, 사람이 아닌 시스템이 먼저 이상을 발견하게 하는 것입니다.

관측성(Observability)은 로그(Logs), 메트릭(Metrics), 트레이스(Traces)라는 세 기둥으로 구성됩니다. 메트릭은 "문제가 있는가"를, 트레이스는 "어디에서 느린가"를, 로그는 "왜 그런가"를 알려 줍니다. 여기에 사용자 영향 기반의 알림과 대시보드를 더해 탐지부터 원인 분석까지 한 흐름으로 연결합니다.

---

## 로그 설계

### 구조화 로그와 상관관계 ID

로그는 사람이 읽는 문장이 아니라 검색과 집계가 가능한 구조화 형식(JSON)으로 남깁니다. 시각, 레벨, 서비스명, 환경, 메시지에 더해 요청 ID(Trace ID), 사용자 ID, 주요 비즈니스 식별자(주문 번호)를 필드로 포함합니다. 하나의 요청이 여러 서비스를 지날 때 같은 ID로 연결할 수 있어야 로그를 추적할 수 있습니다.

### 레벨과 내용의 기준

ERROR는 즉시 조치가 필요한 실패, WARN은 비정상이지만 처리된 상황, INFO는 주요 비즈니스 이벤트, DEBUG는 개발용 상세 정보로 일관되게 구분합니다. 운영에서는 INFO 이상을 기본으로 하고 필요 시 동적으로 레벨을 올립니다. 에러 로그에는 원인(스택 트레이스), 입력 요약, 컨텍스트를 담아 재현 가능한 단서를 제공합니다.

### 남기지 말아야 할 것

비밀번호, 토큰, 카드 번호, 주민번호 같은 민감 정보와 개인정보 원문은 로그에 남기지 않거나 마스킹합니다. 반복 호출되는 루프 안의 과도한 로그는 성능과 비용을 해칩니다. 로그의 보존 기간은 법적 요구와 비용을 고려해 정하고, 접근 권한을 통제합니다.

## 메트릭 설계

### 무엇을 측정할 것인가

서비스 관점의 RED(요청률, 에러율, 지연 분포)와 자원 관점의 USE(사용률, 포화도, 에러)가 기본입니다. 여기에 인프라 지표(CPU, 메모리, 디스크, 네트워크), 런타임 지표(GC, 스레드, 이벤트 루프 지연), 의존성 지표(DB 커넥션 풀, 캐시 적중률, 큐 길이, 외부 API 성공률과 지연)를 더합니다. 비즈니스 지표(주문 수, 결제 성공률, 가입 수)는 기술 지표가 정상이어도 사용자 영향이 있는 문제를 잡아 줍니다.

### 레이블과 카디널리티

메트릭에 레이블(서비스, 엔드포인트, 상태 코드)을 붙이면 분석이 쉬워지지만, 사용자 ID처럼 값의 종류가 무한한 레이블은 시계열 수를 폭발시켜 모니터링 시스템을 무너뜨립니다. 지연은 평균이 아닌 히스토그램으로 수집해 p95, p99를 계산합니다.

## 트레이싱과 상관 분석

분산 트레이싱(OpenTelemetry)은 요청이 각 서비스와 DB, 외부 호출을 지나며 소요한 시간을 스팬(Span)으로 연결해 보여 줍니다. 느린 구간을 즉시 찾고, 서비스 간 호출 관계를 파악하며, 로그와 트레이스 ID로 연결할 수 있습니다. 모든 요청을 수집하면 비용이 크므로 샘플링 전략(비율, 느린 요청과 에러는 항상 수집)을 정합니다.

## 알림과 대시보드

### 사용자 영향 중심 알림

알림은 "CPU 80%" 같은 원인 지표보다 "에러율 5% 초과", "주문 성공률 하락" 같은 사용자 영향 증상에 기반해야 합니다. 모든 알림이 사람을 깨우면 피로가 쌓여 중요한 알림도 무시됩니다. 즉시 조치가 필요한 것(Page)과 업무 시간에 확인할 것(Ticket)을 구분하고, 지속 시간 조건과 SLO 기반 번 레이트(Burn Rate) 알림으로 오탐을 줄입니다. 알림에는 런북 링크와 대시보드 링크를 포함합니다.

### 대시보드

서비스 개요(골든 시그널), 의존성별 상태, 비즈니스 지표를 계층적으로 구성하고, 장애 시 위에서 아래로 좁혀 가며 원인을 찾을 수 있게 만듭니다. 대시보드는 정기적으로 정리하지 않으면 보지 않는 그래프로 가득 찹니다.

---

## 운영과 비용

로그 수집 파이프라인(에이전트, 수집기, 저장소, 검색)의 가용성과 지연을 모니터링하고, 장애 시에도 로그가 유실되지 않도록 버퍼링을 둡니다. 로그와 메트릭 비용은 쉽게 폭증하므로 샘플링, 보존 기간 차등(핫/콜드 저장), 불필요한 로그 제거로 통제합니다. 모니터링 자체가 죽으면 눈이 멀기 때문에 외부 관점의 헬스 체크(합성 모니터링)도 둡니다. 새 기능을 배포할 때 로그와 메트릭, 알림을 함께 정의하는 것을 개발 절차에 포함합니다.

## 예시 코드

### 구조화 로그와 요청 ID 전파

```tsx
import pino from 'pino';
const logger = pino({ level: process.env.LOG_LEVEL ?? 'info' });

app.use((req, res, next) => {
  const requestId = req.get('x-request-id') ?? crypto.randomUUID();
  req.log = logger.child({ requestId, service: 'order-api' });
  res.set('x-request-id', requestId);
  next();
});

req.log.info({ orderId, userId, amount }, 'order created');
req.log.error({ err, orderId }, 'payment failed');
```

### 메트릭 수집 (Prometheus 클라이언트)

```tsx
import client from 'prom-client';

const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status'],      // userId 같은 고카디널리티는 사용 금지
  buckets: [0.05, 0.1, 0.3, 0.5, 1, 2, 5],
});

app.use((req, res, next) => {
  const end = httpDuration.startTimer();
  res.on('finish', () => end({ method: req.method, route: req.route?.path ?? 'unknown', status: res.statusCode }));
  next();
});
```

### 비즈니스 지표 알림 규칙

```yaml
- alert: OrderSuccessRateLow
  expr: |
    sum(rate(orders_total{result="success"}[10m]))
    / sum(rate(orders_total[10m])) < 0.95
  for: 10m
  labels: { severity: page }
  annotations:
    summary: "주문 성공률 95% 미만 (10분 지속)"
    runbook: "https://wiki.example.com/runbooks/order-success-rate"
```

### 민감 정보 로그 차단 (redaction)

```tsx
const logger = pino({
  redact: {
    paths: ['req.headers.authorization', 'password', 'card.number', 'user.ssn'],
    censor: '[REDACTED]',
  },
});
```

## 전체 요약

- 관측성은 로그(왜), 메트릭(문제가 있는가), 트레이스(어디가 느린가)의 세 기둥이며, 함께 연결되어야 탐지부터 원인 분석까지 이어집니다.
- 로그는 구조화(JSON)하고 요청 ID로 서비스 간 추적이 가능하게 하며, 레벨 기준을 일관되게 두고 민감 정보는 남기거나 노출하지 않습니다.
- 메트릭은 RED와 USE, 의존성 지표, 비즈니스 지표를 수집하고, 지연은 히스토그램으로 p95와 p99를 보며, 고카디널리티 레이블을 피합니다.
- 분산 트레이싱으로 구간별 시간을 확인하되 비용을 위해 샘플링 전략을 정합니다.
- 알림은 원인보다 사용자 영향 증상 기반으로, 즉시 조치(Page)와 업무 시간 확인(Ticket)을 구분하고 런북 링크를 포함해 알림 피로를 줄입니다.
- 수집 파이프라인의 가용성과 비용, 외부 합성 모니터링, 기능 개발 시 관측 항목 정의까지 운영 절차에 포함합니다.
