# 요약

백엔드 코드 컨벤션을 정리하면서, 단순히 최종 규칙만 남기지 않고 **왜 이런 규칙을 선택했는지**, **어떤 대안이 있었는지**, **예시 코드는 어떻게 작성되는지**를 함께 기록한다.

이번 정리의 핵심은 다음과 같다.

```
Backend:
Controller → Service → Handler → Repository
Controller = API 요청/응답 변환
Service = 하나의 API 또는 유스케이스 전체 흐름
Handler = 세부 로직
Repository = 데이터 접근

Data Object:
Entity = 영속성 객체
DTO = Entity와 1:1 매칭되는 내부 도메인 데이터 객체
Request = API 입력 객체
Response = API 출력 객체
```

---

# 1. 백엔드 데이터 객체 작성 규칙

## 1.1 최종 규칙

- Entity와 DTO는 1:1로 매칭한다.
- DTO, 요청 객체, 응답 객체는 불변으로 작성한다.
- 데이터 객체 간의 변환은 정적 팩토리 메소드를 선언하여 사용한다.
- 정적 팩토리 메소드는 변환 결과가 되는 데이터 객체의 함수로 작성하여, 해당 데이터 객체의 책임으로 한다.
- 단, Entity가 포함된 변환은 Entity에 정적 팩토리 메소드를 작성하지 않고, DTO, 요청 객체, 응답 객체 등 다른 데이터 객체에 변환 책임을 위임한다.
- 순환 참조 방지를 위해 하위 Entity 또는 DTO는 상위 Entity 또는 DTO를 포함하여 변환하지 않고, 본인 이하의 하위 Entity 또는 DTO만 포함하여 변환한다.
- Entity는 데이터 수정 작업을 제외하고는 조회 후 즉시 DTO로 변환하고 폐기한다.
- 비즈니스 로직 내에서는 Entity 대신 DTO를 도메인 데이터 객체로 활용한다.
- Entity 데이터 수정 작업은 Entity 내부 함수로 작성하고, JPA 더티 체킹을 통해 반영한다.
- 일부 필드만 조회하는 경우에도 Entity와 1:1로 매칭되는 DTO를 사용한다.
- 일부 필드 조회 시 조회하지 않은 DTO 필드는 null로 둘 수 있다.
- API 응답 형태가 다른 경우 DTO를 분리하지 않고, API별 응답 객체를 별도로 작성한다.

---

## 1.2 왜 Entity와 DTO를 1:1로 매칭하는가?

처음 고민은 DTO를 API 응답 형태마다 나눌지, Entity 기준으로 1:1 매칭할지였다.

결론은 **DTO는 Entity와 1:1로 매칭하고, API 응답 형태가 다르면 Response 객체를 별도로 만든다**는 방식이다.

이렇게 하면 DTO가 API 스펙에 끌려다니지 않는다. 예를 들어 게시글 생성 응답, 상세 조회 응답, 목록 조회 응답이 모두 다르더라도 내부 데이터 객체인 `PostDto`는 하나만 유지한다.

```
Post Entity
    ↓
PostDto
    ↓
PostCreateResponse
PostDetailResponse
PostListResponse
```

이 방식의 장점은 다음과 같다.

- DTO가 API별로 계속 늘어나는 것을 막을 수 있다.
- Entity와 DTO의 대응 관계가 명확하다.
- API 응답 스펙 변경은 Response 객체에서 처리할 수 있다.
- 비즈니스 로직에서는 API 응답 형태가 아니라 도메인 데이터 기준으로 작업할 수 있다.

반대로 API별 DTO를 만들면 다음처럼 흐려질 수 있다.

```
PostCreateDto
PostDetailDto
PostListDto
PostSearchDto
PostAdminDto
```

이 경우 DTO가 내부 도메인 데이터 객체인지, API 응답 객체인지 애매해진다.

---

## 1.3 왜 Entity 조회 후 즉시 DTO로 변환하는가?

JPA Entity는 단순 데이터 객체가 아니라 영속성 컨텍스트와 연결되는 객체다. 그래서 비즈니스 로직 전체에서 Entity를 계속 들고 다니면 다음 문제가 생길 수 있다.

- Lazy Loading 발생 시점을 예측하기 어려워진다.
- 트랜잭션 범위에 따라 동작이 달라질 수 있다.
- 의도치 않은 변경이 더티 체킹으로 반영될 수 있다.
- API 응답 직렬화 과정에서 Entity가 노출될 위험이 있다.
- Entity가 여러 레이어에서 사용되면서 책임이 커진다.

그래서 조회 목적의 Entity는 조회 직후 DTO로 변환하고, 비즈니스 로직에서는 DTO를 도메인 데이터 객체처럼 활용한다.

```java
Post post = postRepository.findById(postId)
        .orElseThrow(() -> new IllegalArgumentException("게시글을 찾을 수 없습니다."));

PostDto postDto = PostDto.from(post);
```

단, 수정 작업은 예외다. JPA 더티 체킹을 사용해야 하므로 수정 작업에서는 Entity를 조회하고 Entity 내부 함수를 호출한다.

```java
Post post = postRepository.findById(postId)
        .orElseThrow(() -> new IllegalArgumentException("게시글을 찾을 수 없습니다."));

post.update(request.getTitle(), request.getContent());
```

---

## 1.4 왜 Entity에 DTO 변환 메소드를 두지 않는가?

Entity에 `toDto()` 같은 메소드를 둘 수도 있다.

```java
public PostDto toDto() {
    return PostDto.from(this);
}
```

하지만 이 방식은 비추천한다.

Entity가 DTO를 알게 되면 Entity가 API 계층 또는 애플리케이션 계층의 데이터 객체를 알게 된다. Entity는 영속성/도메인 상태 중심으로 유지하는 게 좋고, DTO/Request/Response 같은 외부 데이터 객체와의 의존은 피하는 게 낫다.

그래서 Entity가 포함된 변환은 Entity가 아니라 다른 데이터 객체에 책임을 둔다.

```java
PostDto postDto = PostDto.from(post);
PostCreateResponse response = PostCreateResponse.from(postDto);
```

정리하면 다음과 같다.

```
허용:
PostDto.from(Post post)
PostCreateResponse.from(PostDto postDto)
PostCreateRequest.toEntity()

비추천:
post.toDto()
post.toResponse()
```

---

## 1.5 Request.toEntity는 허용해도 되는가?

요청 객체에서 Entity를 생성하는 것은 허용한다.

```java
Post post = request.toEntity();
```

이유는 생성 요청 객체는 API 입력값을 기반으로 새로운 Entity를 만드는 책임을 가질 수 있기 때문이다. 단, 이 규칙은 생성에 한정하는 것이 좋다.

수정은 `request.toEntity()`로 새 Entity를 만드는 방식이 아니라, 기존 Entity를 조회한 뒤 Entity 내부 수정 함수를 호출한다.

```java
// 생성
Post post = request.toEntity();
postRepository.save(post);

// 수정
Post post = postRepository.findById(postId).orElseThrow();
post.update(request.getTitle(), request.getContent());
```

DTO에서 Entity를 다시 만드는 메소드는 두지 않는 편이 좋다.

```java
// 비추천
Post post = postDto.toEntity();
```

DTO에서 Entity를 새로 만들면 JPA 영속성, 식별자, 연관관계, 더티 체킹 흐름이 헷갈릴 수 있다.

---

## 1.6 일부 필드만 조회하는 경우 DTO는 어떻게 처리하는가?

일부 필드만 조회하는 경우에도 Entity와 1:1로 매칭되는 DTO를 사용한다. 조회하지 않은 필드는 `null`로 둘 수 있다.

```java
public static PostDto listOf(Long id, String title, String authorName) {
    return new PostDto(
            id,
            title,
            null,
            authorName
    );
}
```

이 방식의 장점은 DTO 종류가 늘어나지 않는다는 점이다.

```
PostDto 하나만 유지
PostListDto, PostSearchDto, PostSummaryDto 남발 방지
```

다만 주의할 점도 있다. 일부 필드만 채워진 DTO가 상세 응답 변환에 잘못 사용되면 `content = null` 같은 문제가 생길 수 있다.

그래서 일부 필드 DTO는 용도를 드러내는 정적 팩토리 메소드를 사용한다.

```java
PostDto.from(post);       // 전체 Entity 기반 DTO
PostDto.listOf(...);      // 목록 조회용 DTO
PostDto.searchOf(...);    // 검색 조회용 DTO
```

또한 일부 필드만 채워진 DTO는 해당 조회 목적에 맞는 Response 변환에만 사용한다.

## 1.7 데이터 객체 예시 코드

```java
// ============================================================
// Entity
// - Entity와 DTO는 1:1로 매칭한다.
// - Entity에는 DTO 변환 메소드를 작성하지 않는다.
// - Entity 수정은 Entity 내부 함수로 처리한다.
// ============================================================

@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id; // 게시글 ID

    private String title; // 제목

    private String content; // 내용

    private String authorName; // 작성자명

    private Post(String title, String content, String authorName) {
        this.title = title;
        this.content = content;
        this.authorName = authorName;
    }

    public static Post create(String title, String content, String authorName) {
        return new Post(title, content, authorName);
    }

    public void update(String title, String content) {
        this.title = title;
        this.content = content;
    }
}
```

```java
// ============================================================
// DTO
// - Entity와 1:1 매칭한다.
// - Entity 조회 후 즉시 DTO로 변환하여 사용한다.
// - 일부 필드 조회 시 조회하지 않은 필드는 null로 둘 수 있다.
// ============================================================

@Getter
public final class PostDto {

    private final Long id;
    private final String title;
    private final String content;
    private final String authorName;

    private PostDto(Long id, String title, String content, String authorName) {
        this.id = id;
        this.title = title;
        this.content = content;
        this.authorName = authorName;
    }

    public static PostDto from(Post post) {
        return new PostDto(
                post.getId(),
                post.getTitle(),
                post.getContent(),
                post.getAuthorName()
        );
    }

    public static PostDto listOf(Long id, String title, String authorName) {
        return new PostDto(
                id,
                title,
                null,
                authorName
        );
    }
}
```

```java
// ============================================================
// Request
// - API 요청 객체는 불변으로 작성한다.
// - Entity 생성이 필요한 경우 Request에서 Entity를 생성한다.
// ============================================================

@Getter
public final class PostCreateRequest {

    private final Long memberId;
    private final String title;
    private final String content;
    private final String authorName;

    @JsonCreator
    public PostCreateRequest(
            @JsonProperty("memberId") Long memberId,
            @JsonProperty("title") String title,
            @JsonProperty("content") String content,
            @JsonProperty("authorName") String authorName
    ) {
        this.memberId = memberId;
        this.title = title;
        this.content = content;
        this.authorName = authorName;
    }

    public Post toEntity() {
        return Post.create(
                title,
                content,
                authorName
        );
    }
}
```

```java
// ============================================================
// Response
// - API 응답 객체는 불변으로 작성한다.
// - API 응답 형태별로 별도 Response를 작성한다.
// - DTO → Response 변환 책임은 Response가 가진다.
// ============================================================

@Getter
public final class PostCreateResponse {

    private final Long id;
    private final String title;

    private PostCreateResponse(Long id, String title) {
        this.id = id;
        this.title = title;
    }

    public static PostCreateResponse from(PostDto postDto) {
        return new PostCreateResponse(
                postDto.getId(),
                postDto.getTitle()
        );
    }
}

@Getter
public final class PostDetailResponse {

    private final Long id;
    private final String title;
    private final String content;
    private final String authorName;

    private PostDetailResponse(
            Long id,
            String title,
            String content,
            String authorName
    ) {
        this.id = id;
        this.title = title;
        this.content = content;
        this.authorName = authorName;
    }

    public static PostDetailResponse from(PostDto postDto) {
        return new PostDetailResponse(
                postDto.getId(),
                postDto.getTitle(),
                postDto.getContent(),
                postDto.getAuthorName()
        );
    }
}

@Getter
public final class PostListResponse {

    private final Long id;
    private final String title;
    private final String authorName;

    private PostListResponse(Long id, String title, String authorName) {
        this.id = id;
        this.title = title;
        this.authorName = authorName;
    }

    public static PostListResponse from(PostDto postDto) {
        return new PostListResponse(
                postDto.getId(),
                postDto.getTitle(),
                postDto.getAuthorName()
        );
    }
}
```

# 2. 백엔드 레이어 호출 규칙

## 2.1 최종 규칙

- Controller 함수는 하나의 Service 함수만 호출한다.
- Controller는 API 요청 객체를 받아 바로 Service로 건네주며, DTO를 응답 객체로 변환하여 반환한다.
- Service 함수는 하나의 API에 대한 전체 비즈니스 로직 흐름을 담당한다.
- Service는 요청 객체를 건네받고, DTO를 반환한다.
- Service 함수는 로직 단위로 여러 Handler 함수를 호출할 수 있다.
- Service는 다른 도메인의 Handler도 호출할 수 있다.
- Service 함수가 `@Transactional`을 담당한다.
- Handler 함수는 Service에서만 호출할 수 있다.
- Handler 함수 하나는 하나의 세부 로직만 담당한다.
- Handler는 필요시 도메인의 Repository를 호출하여 Entity를 조회, 저장, 수정, 삭제하고 DTO로 변환한다.
- Handler는 자기 도메인의 Repository만 호출할 수 있다.
- Repository는 데이터 접근 책임만 가진다.
- Repository는 Entity를 반환한다.
- 커스텀 Repository는 조회 목적에 따라 Entity 또는 DTO를 반환할 수 있다.

---

## 2.2 Controller는 왜 하나의 Service 함수만 호출하는가?

Controller는 HTTP 요청과 응답의 경계다. 그래서 Controller가 여러 Service나 Handler를 직접 호출하기 시작하면 비즈니스 흐름이 Controller에 섞인다.

비추천 흐름은 다음과 같다.

```java
@PostMapping
public ResponseEntity<PostCreateResponse> createPost(@RequestBody PostCreateRequest request) {
    memberService.validateMember(request.getMemberId());
    postService.validateCreate(request);
    PostDto postDto = postService.create(request);
    return ResponseEntity.ok(PostCreateResponse.from(postDto));
}
```

이렇게 되면 Controller가 전체 비즈니스 흐름을 알게 된다. Controller는 얇게 유지하고, 하나의 Service 함수만 호출한다.

```java
@PostMapping
public ResponseEntity<PostCreateResponse> createPost(@RequestBody PostCreateRequest request) {
    PostDto postDto = postService.createPost(request);
    return ResponseEntity.ok(PostCreateResponse.from(postDto));
}
```

---

## 2.3 Service는 왜 전체 비즈니스 흐름을 담당하는가?

Service 함수는 하나의 API 또는 유스케이스에 대한 전체 흐름을 보여주는 위치다.

예를 들어 게시글 생성 API의 흐름은 다음과 같이 읽혀야 한다.

```
1. 회원 검증
2. 게시글 생성 검증
3. 게시글 생성
4. 게시글 생성 이벤트 발행
5. DTO 반환
```

이 흐름이 Service에 있으면 코드를 읽는 사람이 API 동작을 빠르게 이해할 수 있다.

```java
@Transactional
public PostDto createPost(PostCreateRequest request) {
    memberValidateHandler.validateWritableMember(request.getMemberId());
    postValidateHandler.validateCreate(request);
    PostDto postDto = postCreateHandler.create(request);
    postEventHandler.publishCreated(postDto);
    return postDto;
}
```

---

## 2.4 Service는 Response를 반환할까 DTO를 반환할까?

중간에 고민했던 부분은 Service가 Response를 반환할지, DTO를 반환할지였다.

첫 번째 방식은 Service가 Response를 반환하는 구조다.

```java
public PostCreateResponse createPost(PostCreateRequest request) {
    PostDto postDto = postCreateHandler.create(request);
    return PostCreateResponse.from(postDto);
}
```

이 방식은 Controller가 매우 얇아진다. 하지만 Service가 API 응답 객체를 알게 된다.

두 번째 방식은 Service가 DTO를 반환하고 Controller가 Response로 변환하는 구조다.

```java
public PostDto createPost(PostCreateRequest request) {
    return postCreateHandler.create(request);
}
```

```java
@PostMapping
public ResponseEntity<PostCreateResponse> createPost(@RequestBody PostCreateRequest request) {
    PostDto postDto = postService.createPost(request);
    return ResponseEntity.ok(PostCreateResponse.from(postDto));
}
```

최종 선택은 **Service는 DTO를 반환하고 Controller가 Response를 변환한다**는 방식이다.

이렇게 하면 Service는 API 응답 스펙에서 조금 더 분리되고, Controller가 HTTP/API 출력 변환 책임을 가진다.

---

## 2.5 Service는 다른 도메인의 Handler를 호출해도 되는가?

가능하다. 오히려 다른 도메인의 Repository를 직접 호출하는 것보다 이 방식이 낫다.

예를 들어 게시글 생성 시 회원 검증이 필요하다면 다음 방식이 좋다.

```
PostService → MemberValidateHandler → MemberRepository
```

이 방식은 허용한다.

반대로 다음 방식은 비추천한다.

```
PostValidateHandler → MemberRepository
```

Post 도메인의 Handler가 Member Repository를 직접 알게 되면 Member 도메인의 내부 구현에 의존하게 된다. 그러면 도메인 경계가 흐려진다.

그래서 다른 도메인 검증이 필요할 때는 Service가 해당 도메인의 Handler를 호출한다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class PostService {

    private final MemberValidateHandler memberValidateHandler;
    private final PostValidateHandler postValidateHandler;
    private final PostCreateHandler postCreateHandler;

    @Transactional
    public PostDto createPost(PostCreateRequest request) {
        memberValidateHandler.validateWritableMember(request.getMemberId());
        postValidateHandler.validateCreate(request);
        return postCreateHandler.create(request);
    }
}
```

---

## 2.6 Handler는 왜 Service에서만 호출하는가?

Handler는 세부 로직 단위다. 예를 들어 검증, 생성, 이벤트 발행, 외부 API 호출 같은 작업을 담당한다.

Handler가 다른 Handler를 직접 호출하기 시작하면 전체 흐름이 Service 밖으로 숨어버린다.

비추천 흐름은 다음과 같다.

```java
@Component
public class PostCreateHandler {

    private final PostValidateHandler postValidateHandler;
    private final PostRepository postRepository;

    public PostDto create(PostCreateRequest request) {
        postValidateHandler.validateCreate(request);
        Post post = request.toEntity();
        return PostDto.from(postRepository.save(post));
    }
}
```

이렇게 되면 Service에서는 `postCreateHandler.create(request)`만 보이고, 내부에서 어떤 검증이 수행되는지 흐름이 숨는다.

추천 흐름은 Service에서 Handler 호출 순서를 제어하는 것이다.

```java
@Transactional
public PostDto createPost(PostCreateRequest request) {
    postValidateHandler.validateCreate(request);
    return postCreateHandler.create(request);
}
```

정리하면 다음과 같다.

```
Handler는 Service에서만 호출한다.
Handler끼리 직접 호출하지 않는다.
Handler 호출 순서는 Service 함수에서 제어한다.
```

---

## 2.7 Handler가 다른 도메인 Repository를 호출하는 것은 괜찮은가?

결론은 **비추천**이다.

가능은 하지만, 컨벤션상 막는 것이 좋다.

비추천 예시는 다음과 같다.

```java
@Component
@RequiredArgsConstructor
public class PostValidateHandler {

    private final MemberRepository memberRepository;

    public void validateCreate(PostCreateRequest request) {
        Member member = memberRepository.findById(request.getMemberId())
                .orElseThrow();

        if (member.isBlocked()) {
            throw new IllegalArgumentException("차단된 회원입니다.");
        }
    }
}
```

이렇게 하면 `PostValidateHandler`가 `Member` 도메인의 DB 구조와 정책을 알게 된다.

더 나은 방식은 다음과 같다.

```java
@Component
@RequiredArgsConstructor
public class MemberValidateHandler {

    private final MemberRepository memberRepository;

    public void validateWritableMember(Long memberId) {
        Member member = memberRepository.findById(memberId)
                .orElseThrow(() -> new IllegalArgumentException("회원을 찾을 수 없습니다."));

        if (member.isBlocked()) {
            throw new IllegalArgumentException("차단된 회원입니다.");
        }
    }
}
```

```java
@Transactional
public PostDto createPost(PostCreateRequest request) {
    memberValidateHandler.validateWritableMember(request.getMemberId());
    postValidateHandler.validateCreate(request);
    return postCreateHandler.create(request);
}
```

정리하면 다음 규칙이 된다.

```
Service는 여러 도메인의 Handler를 호출할 수 있다.
Handler는 자기 도메인의 Repository만 호출한다.
다른 도메인의 Repository가 필요하면 Service에서 해당 도메인의 Handler를 호출한다.
```

---

## 2.8 Transaction은 왜 Service에서 담당하는가?

트랜잭션은 하나의 API 또는 유스케이스 전체 흐름에 대한 경계다.

Handler마다 `@Transactional`을 붙이면 전체 흐름의 원자성이 애매해질 수 있다.

비추천 예시는 다음과 같다.

```java
@Component
public class PostCreateHandler {

    @Transactional
    public PostDto create(PostCreateRequest request) {
        ...
    }
}
```

추천 방식은 Service 함수에 트랜잭션을 선언하는 것이다.

```java
@Service
@Transactional(readOnly = true)
public class PostService {

    @Transactional
    public PostDto createPost(PostCreateRequest request) {
        memberValidateHandler.validateWritableMember(request.getMemberId());
        postValidateHandler.validateCreate(request);
        return postCreateHandler.create(request);
    }
}
```

이렇게 하면 게시글 생성 API의 전체 흐름이 하나의 트랜잭션 안에서 처리된다.

## 2.9 Repository와 Custom Repository 반환 기준

기본 Repository는 Entity를 반환한다.

```java
public interface PostRepository extends JpaRepository<Post, Long> {
    Optional<Post> findById(Long id);
    boolean existsByTitle(String title);
}
```

커스텀 Repository 또는 QueryRepository는 조회 목적에 따라 Entity 또는 DTO를 반환할 수 있다.

복잡한 목록 조회나 일부 필드 조회에서는 DTO를 바로 반환해도 된다.

```java
@Repository
@RequiredArgsConstructor
public class PostQueryRepository {

    private final JPAQueryFactory queryFactory;

    public List<PostDto> findPostList() {
        return queryFactory
                .select(Projections.constructor(
                        PostListProjection.class,
                        post.id,
                        post.title,
                        post.authorName
                ))
                .from(post)
                .fetch()
                .stream()
                .map(PostListProjection::toDto)
                .toList();
    }
}
```

정리하면 다음과 같다.

```
Repository = 기본 Entity 중심 데이터 접근
Custom Repository / QueryRepository = 복잡한 조회, 일부 필드 조회, DTO 반환 가능
```

## 2.10 레이어 호출 예시 코드

```java
// ============================================================
// Controller
// - Controller 함수는 하나의 Service 함수만 호출한다.
// - Service가 반환한 DTO를 응답 객체로 변환하여 반환한다.
// ============================================================

@RestController
@RequiredArgsConstructor
@RequestMapping("/api/posts")
public class PostController {

    private final PostService postService;

    @PostMapping
    public ResponseEntity<PostCreateResponse> createPost(
            @RequestBody PostCreateRequest request
    ) {
        PostDto postDto = postService.createPost(request);

        return ResponseEntity.ok(
                PostCreateResponse.from(postDto)
        );
    }
}
```

```java
// ============================================================
// Service
// - Service 함수는 전체 비즈니스 로직 흐름을 담당한다.
// - Service 함수가 @Transactional을 담당한다.
// - Service는 여러 Handler를 호출하고 DTO를 반환한다.
// ============================================================

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class PostService {

    private final MemberValidateHandler memberValidateHandler; // 다른 도메인 Handler
    private final PostValidateHandler postValidateHandler;
    private final PostCreateHandler postCreateHandler;
    private final PostEventHandler postEventHandler;

    @Transactional
    public PostDto createPost(PostCreateRequest request) {

        // 1. 회원 검증
        memberValidateHandler.validateWritableMember(request.getMemberId());

        // 2. 게시글 생성 검증
        postValidateHandler.validateCreate(request);

        // 3. 게시글 생성
        PostDto postDto = postCreateHandler.create(request);

        // 4. 게시글 생성 후처리
        postEventHandler.publishCreated(postDto);

        // 5. DTO 반환
        return postDto;
    }
}
```

```java
// ============================================================
// Handler
// - Handler 함수는 Service에서만 호출한다.
// - Handler 함수 하나는 하나의 세부 로직만 담당한다.
// - Handler는 자기 도메인의 Repository만 호출한다.
// ============================================================

@Component
@RequiredArgsConstructor
public class MemberValidateHandler {

    private final MemberRepository memberRepository;

    public void validateWritableMember(Long memberId) {
        Member member = memberRepository.findById(memberId)
                .orElseThrow(() -> new IllegalArgumentException("회원을 찾을 수 없습니다."));

        if (member.isBlocked()) {
            throw new IllegalArgumentException("차단된 회원입니다.");
        }
    }
}

@Component
@RequiredArgsConstructor
public class PostValidateHandler {

    private final PostRepository postRepository;

    public void validateCreate(PostCreateRequest request) {
        boolean existsTitle = postRepository.existsByTitle(request.getTitle());

        if (existsTitle) {
            throw new IllegalArgumentException("이미 존재하는 제목입니다.");
        }
    }
}

@Component
@RequiredArgsConstructor
public class PostCreateHandler {

    private final PostRepository postRepository;

    public PostDto create(PostCreateRequest request) {
        Post post = request.toEntity();
        Post savedPost = postRepository.save(post);
        return PostDto.from(savedPost);
    }
}

@Component
@RequiredArgsConstructor
public class PostEventHandler {

    private final ApplicationEventPublisher eventPublisher;

    public void publishCreated(PostDto postDto) {
        eventPublisher.publishEvent(
                PostCreatedEvent.from(postDto)
        );
    }
}
```

```java
// ============================================================
// Repository
// - Repository는 데이터 접근 책임만 가진다.
// - Repository는 Entity를 반환한다.
// ============================================================

public interface PostRepository extends JpaRepository<Post, Long> {
    boolean existsByTitle(String title);
}

public interface MemberRepository extends JpaRepository<Member, Long> {
}
```

# 3. 최종 정리

이 컨벤션은 단순 CRUD 프로젝트보다는 API 수가 많고, 비즈니스 흐름이 복잡한 서비스에 더 잘 맞는다.

장점은 다음과 같다.

```
일관성: 높음
가독성: 중상
유지보수성: 중상
확장성: 높음
초기 작성 비용: 높음
단순 CRUD 생산성: 낮음
복잡한 비즈니스 로직 대응력: 높음
```

서비스가 많고 팀원이 여러 명이면, 정해진 틀 안에서 비슷한 형태의 코드를 만들 수 있다는 장점이 크다.

반면 단순 게시판 수준에서는 과할 수 있다. Controller, Service, Handler, Repository, DTO, Request, Response를 모두 만들면 파일 수가 많아진다.
