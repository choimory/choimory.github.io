# 요약

백엔드 코드 컨벤션을 `데이터 객체`, `레이어 호출 규칙`처럼 요소별로 나눈 것처럼, 프론트엔드 코드 컨벤션도 역할 단위로 나누어 정리한다.

Next.js + TypeScript 기준으로 프론트엔드는 다음 요소를 중심으로 분리한다.

```
Page = 라우팅 진입점
Container = 화면 흐름 제어
Component = UI 렌더링
Custom Hook = 상태와 이벤트 로직
API Module = 서버 통신
Data Object = 요청/응답 타입, ViewModel, Props
Mapper = API 응답을 화면 데이터로 변환
State = 화면 상태 또는 전역 상태 관리
```

이 구조의 핵심은 **화면 진입, 화면 흐름, 상태 처리, API 호출, UI 렌더링 책임을 분리하는 것**이다.

# 1. 프론트엔드 기본 구조 작성 규칙

## 1.1 최종 규칙

- 화면은 `page`, `container`, `component` 단위로 분리한다.
- `page`는 라우팅 진입점 역할만 담당한다.
- `container`는 API 호출, 상태 관리, 이벤트 흐름 등 화면의 로직을 담당한다.
- `component`는 UI 렌더링만 담당한다.
- 공통 UI는 `components/common` 또는 `shared/ui`에 작성한다.
- 도메인별 화면과 컴포넌트는 도메인 폴더 내부에 작성한다.
- 하나의 컴포넌트는 하나의 주요 책임만 가진다.
- 컴포넌트가 커지면 UI 단위 또는 로직 단위로 분리한다.

## 1.2 왜 이렇게 나누는가?

프론트엔드 코드는 화면 안에 API 호출, 상태 관리, 이벤트 처리, 렌더링 코드가 쉽게 섞인다.

예를 들어 `page.tsx` 안에서 다음을 모두 처리하면 파일이 빠르게 커진다.

- API 호출
- loading 상태
- form 상태
- submit 이벤트
- 응답 데이터 가공
- UI 렌더링

그래서 화면을 다음처럼 역할별로 나눈다.

```
Page
  ↓
Container
  ↓
Custom Hook / API Module
  ↓
Component
```

이렇게 하면 `page`는 얇아지고, `container`는 화면 흐름만 제어하고, `component`는 순수하게 UI 렌더링에 집중할 수 있다.

## 1.3 예시 폴더 구조

```
src
├── app
│   └── posts
│       └── page.tsx
│
├── features
│   └── post
│       ├── api
│       │   └── postApi.ts
│       ├── model
│       │   └── postTypes.ts
│       ├── container
│       │   └── PostCreateContainer.tsx
│       ├── components
│       │   └── PostCreateForm.tsx
│       └── hooks
│           └── usePostCreate.ts
│
└── shared
    ├── api
    ├── ui
    └── utils
```

# 2. 프론트엔드 데이터 객체 작성 규칙

## 2.1 최종 규칙

- API 요청 타입과 응답 타입은 명확하게 분리한다.
- API 응답 타입을 화면 컴포넌트에서 직접 변경하지 않는다.
- 화면에서 사용하는 데이터 형태가 API 응답과 다르면 ViewModel 타입을 별도로 작성한다.
- API 응답 객체를 ViewModel로 변환하는 함수는 별도 mapper 함수로 작성한다.
- 컴포넌트 props 타입은 해당 컴포넌트 파일 내부 또는 가까운 위치에 작성한다.
- 도메인 공통 타입은 `model` 또는 `types` 파일에 작성한다.
- `any` 사용은 금지하고, 불가피하면 `unknown` 사용 후 타입 가드를 작성한다.

## 2.2 왜 요청 타입과 응답 타입을 분리하는가?

요청과 응답은 생김새가 비슷해 보여도 책임이 다르다.

```
Request = 서버에 보내는 데이터
Response = 서버에서 받는 데이터
ViewModel = 화면에서 사용하기 좋게 가공한 데이터
Props = 컴포넌트에 전달하는 데이터
```

API 응답을 화면에서 그대로 사용하면 백엔드 응답 구조가 화면 구조에 직접 영향을 준다.

예를 들어 서버 응답 필드가 `authorName`인데 화면에서는 `author`라는 이름이 더 자연스러울 수 있다. 이때 컴포넌트 내부에서 직접 바꾸기보다는 mapper를 통해 ViewModel로 변환하는 것이 좋다.

## 2.3 예시 코드

```tsx
// postTypes.ts

export type PostCreateRequest = {
  title: string;
  content: string;
};

export type PostCreateResponse = {
  id: number;
  title: string;
};

export type PostDetailResponse = {
  id: number;
  title: string;
  content: string;
  authorName: string;
};

export type PostViewModel = {
  id: number;
  title: string;
  content: string;
  author: string;
};

export const toPostViewModel = (
  response: PostDetailResponse
): PostViewModel => ({
  id: response.id,
  title: response.title,
  content: response.content,
  author: response.authorName,
});
```

# 3. 프론트엔드 API 호출 작성 규칙

## 3.1 최종 규칙

- API 호출 함수는 컴포넌트 내부에 직접 작성하지 않는다.
- API 호출은 도메인별 `api` 파일에 작성한다.
- API 함수는 요청 객체를 받고 응답 객체를 반환한다.
- HTTP client 설정은 공통 모듈에서 관리한다.
- API 에러는 공통 에러 처리 규칙을 따른다.
- API URL 문자열은 컴포넌트에 직접 작성하지 않는다.
- React Query를 사용하는 경우 query key는 도메인별 상수로 관리한다.

## 3.2 왜 API 호출을 컴포넌트에서 분리하는가?

컴포넌트 내부에서 직접 API를 호출하면 UI 렌더링 책임과 서버 통신 책임이 섞인다.

```tsx
// 비추천
export function PostCreateForm() {
  const handleSubmit = async () => {
    await axios.post('/api/posts', { title, content });
  };

  return <form>...</form>;
}
```

이렇게 되면 컴포넌트가 다음 책임을 모두 갖게 된다.

- 입력 상태 관리
- API URL 관리
- HTTP client 사용
- 에러 처리
- UI 렌더링

그래서 API 호출은 도메인별 API 모듈로 분리한다.

## 3.3 예시 코드

```tsx
// postApi.ts

import { apiClient } from '@/shared/api/apiClient';
import type {
  PostCreateRequest,
  PostCreateResponse,
  PostDetailResponse,
} from '../model/postTypes';

export const postApi = {
  createPost: async (
    request: PostCreateRequest
  ): Promise<PostCreateResponse> => {
    const { data } = await apiClient.post<PostCreateResponse>(
      '/api/posts',
      request
    );

    return data;
  },

  getPost: async (postId: number): Promise<PostDetailResponse> => {
    const { data } = await apiClient.get<PostDetailResponse>(
      `/api/posts/${postId}`
    );

    return data;
  },
};
```

# 4. 프론트엔드 Component 작성 규칙

## 4.1 최종 규칙

- 컴포넌트는 가능한 한 props를 통해 데이터를 전달받는다.
- UI 컴포넌트는 API 호출을 직접 수행하지 않는다.
- UI 컴포넌트는 전역 상태에 직접 의존하지 않는다.
- 이벤트 함수는 `handle` 접두사를 사용한다.
- boolean props는 `is`, `has`, `can`, `should` 접두사를 사용한다.
- 컴포넌트 파일명은 PascalCase로 작성한다.
- hook 파일명은 `use` 접두사를 사용한다.
- 하나의 파일에는 하나의 주요 컴포넌트만 작성한다.

## 4.2 왜 UI 컴포넌트는 API와 전역 상태에 직접 의존하지 않는가?

UI 컴포넌트는 재사용성이 중요하다.

컴포넌트가 API 호출이나 전역 상태에 직접 의존하면 특정 화면에서만 사용할 수 있는 컴포넌트가 된다.

반대로 props 기반으로 작성하면 같은 컴포넌트를 다른 화면에서도 재사용하기 쉽다.

```
좋음:
Container → props → Component

비추천:
Component → API 직접 호출
Component → 전역 상태 직접 접근
```

## 4.3 예시 코드

```tsx
// PostCreateForm.tsx

type PostCreateFormProps = {
  title: string;
  content: string;
  isSubmitting: boolean;
  onChangeTitle: (title: string) => void;
  onChangeContent: (content: string) => void;
  onSubmit: () => void;
};

export function PostCreateForm({
  title,
  content,
  isSubmitting,
  onChangeTitle,
  onChangeContent,
  onSubmit,
}: PostCreateFormProps) {
  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        onSubmit();
      }}
    >
      <input
        value={title}
        onChange={(event) => onChangeTitle(event.target.value)}
      />

      <textarea
        value={content}
        onChange={(event) => onChangeContent(event.target.value)}
      />

      <button type="submit" disabled={isSubmitting}>
        등록
      </button>
    </form>
  );
}
```

# 5. 프론트엔드 Container / Hook 작성 규칙

## 5.1 최종 규칙

- Container는 화면의 데이터 흐름과 이벤트 흐름을 담당한다.
- 복잡한 상태와 이벤트 로직은 custom hook으로 분리한다.
- custom hook은 상태, 이벤트 함수, 비동기 처리 결과를 반환한다.
- custom hook은 UI를 반환하지 않는다.
- Container는 hook 결과를 UI 컴포넌트에 props로 전달한다.

## 5.2 왜 Container와 Hook을 분리하는가?

Container는 화면을 조립하고, Hook은 상태와 이벤트 로직을 담당한다.

둘을 분리하면 화면 구조와 로직 구조를 따로 볼 수 있다.

```
Container = 어떤 UI 컴포넌트에 어떤 데이터를 전달할지 결정
Hook = 상태, 이벤트, 비동기 처리 로직 담당
Component = 전달받은 props로 UI 렌더링
```

## 5.3 Custom Hook 예시 코드

```tsx
// usePostCreate.ts

import { useState } from 'react';
import { postApi } from '../api/postApi';

export function usePostCreate() {
  const [title, setTitle] = useState('');
  const [content, setContent] = useState('');

  const [isSubmitting, setIsSubmitting] = useState(false);

  const handleSubmit = async () => {
    setIsSubmitting(true);

    try {
      await postApi.createPost({
        title,
        content,
      });
    } finally {
      setIsSubmitting(false);
    }
  };

  return {
    title,
    content,
    isSubmitting,
    setTitle,
    setContent,
    handleSubmit,
  };
}
```

## 5.4 Container 예시 코드

```tsx
// PostCreateContainer.tsx

import { PostCreateForm } from '../components/PostCreateForm';
import { usePostCreate } from '../hooks/usePostCreate';

export function PostCreateContainer() {
  const {
    title,
    content,
    isSubmitting,
    setTitle,
    setContent,
    handleSubmit,
  } = usePostCreate();

  return (
    <PostCreateForm
      title={title}
      content={content}
      isSubmitting={isSubmitting}
      onChangeTitle={setTitle}
      onChangeContent={setContent}
      onSubmit={handleSubmit}
    />
  );
}
```

# 6. 프론트엔드 Page 작성 규칙

## 6.1 최종 규칙

- `page.tsx`는 가능한 얇게 유지한다.
- `page.tsx`에서는 화면 Container를 호출한다.
- page에서 직접 API 호출, 복잡한 상태 관리, 이벤트 로직을 작성하지 않는다.
- Next.js 서버 컴포넌트에서 필요한 초기 데이터 조회는 page 또는 server action에서 수행할 수 있다.
- 클라이언트 상호작용이 필요한 영역은 Client Component로 분리한다.

## 6.2 왜 Page를 얇게 유지하는가?

Next.js에서 `page.tsx`는 라우팅 진입점이다.

`page.tsx`에 화면 로직이 많아지면 라우팅, 데이터 조회, 상태 관리, UI 렌더링 책임이 모두 섞인다.

그래서 page는 화면 Container를 호출하는 정도로 얇게 유지한다.

## 6.3 예시 코드

```tsx
// app/posts/create/page.tsx

import { PostCreateContainer } from '@/features/post/container/PostCreateContainer';

export default function PostCreatePage() {
  return <PostCreateContainer />;
}
```

# 7. 핵심 흐름 요약

```
Page
  ↓
Container
  ↓
Custom Hook
  ↓
API Module
  ↓
Response
  ↓
Mapper
  ↓
ViewModel
  ↓
Component Props
  ↓
Component Rendering
```

프론트도 이 정도로 맞추면 균형이 좋다.

```
Backend:
Controller → Service → Handler → Repository

Frontend:
Page → Container → Hook/API → Component
```
